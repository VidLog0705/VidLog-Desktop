## 1. 扫码枪判定（规格 §3.2.1）

判定规则是「**短时间内的连续按键 + 结束符**」，规格没给具体数值。

| 参数 | 取值 | 依据 |
|---|---|---|
| 相邻按键最大间隔 | **50 ms** | USB HID 扫码枪通常 1~10 ms/键，偶尔到 30 ms；人类打字再快也在 80 ms 以上 |
| 最短长度 | 5 | 太短的串不可能是单号 |
| 最长长度 | 40 | 超过即误触 |
| 结束符 | `\r` `\n` `\t` | 扫码枪普遍发 Enter |

**「不能吞掉用户正常打字」靠三层保证**：

1. 间隔超阈值 → 判定为人类输入，整串放弃
2. 串里出现单号不可能有的字符（空格、`/`、`@`、中文……）→ 放弃
3. 长度越界 → 放弃

人类要以 50 ms 以内的间隔敲出 5 个以上合法单号字符再按回车，实际上不可能。

### 1.1 键盘自动重复（实现中发现，规格没提）

**按住某键不放时，Windows 的自动重复间隔约 30 ms —— 落在 50 ms 阈值之内。**
所以在「按住一个字母键 + 敲回车」的场景下，会被误判成一次扫码。

防护：**整串字符完全相同就放弃**。自动重复必产生一串相同字符，而真实单号极少全同。
代价是形如 `000000000000` 的单号会漏判 —— 极罕见，且漏判只退化成手动输入，
不会误吞用户输入。

> 判定逻辑做成对按键流的**纯函数**（`ScannerKeystrokeDetector`），不接触键盘、不吞按键。
> 接触键盘的是平台层（Windows 全局钩子），那是投递，不是判定 —— 分开才能把
> 「阈值、边界、误判」这些最容易错的部分完整测到。

## 2. 录像链路（规格 §3.1.4 / §3.1.5）

### 2.1 为什么录制期写 MKV、停下来再 remux 成 MP4

MP4 的索引（`moov`）在**文件末尾**。进程被杀时那段没写下去，整个文件就是彻底打不开的废件
—— 正好撞上规格 §8 的「录制中掉电/进程被杀」和 I9 的「不产生无法播放的半成品」。

MKV 是分段结构，写到哪算哪，剩余的也能解出来。

所以：**录制期 MKV 中间容器 → 停止后 `-c copy` 无损 remux → MP4 成品**。
`-c copy` 不重编码，画面零损失，也快。加了 `-movflags +faststart` 把 moov 挪到文件头。

### 2.2 编码能力必须实测，不能查表

`ffmpeg -encoders` 列出的是「**编译进去了**」，不是「**这台机器能跑**」。

本机实测（2026-09-16）：

| 编码器 | 列表里 | 实测 |
|---|---|---|
| `libx264` / `libx265` / `h264_qsv` | 有 | ✅ 能出片 |
| `h264_nvenc` | 有 | ❌ 无 NVIDIA 卡 |
| `h264_amf` | 有 | ❌ 无 AMD 卡 |
| `hevc_qsv` | 有 | ❌ HD 630 上 qsv 编不了 HEVC |

**8 个里只有 3 个真能用。** 所以 `FfmpegEncoderProbe` 是**真编一小段再解码验一遍**。

另外注意：失败退出码五花八门（实测见过 `-1`、`-1313558101`、`-40`），
而且**退出码为 0 也可能是空产物** —— 所以判据是「产物存在 + 非空 + 真能解码」，
不是「退出码等于 0」。

候选顺序：`h264_nvenc` → `h264_qsv` → `h264_amf` → `libx264`（硬件优先，软件兜底）。
取第一个**实测可用**的。

### 2.3 成品校验是「真解一遍」

`DecodeVerifier` 跑 `ffmpeg -v error -i <成品> -f null -`，判据两条：

1. 退出码为 0
2. **stderr 为空**

第二条不能省：FFmpeg 遇到损坏的流常常**照样退 0**，只是往 stderr 里骂。
只检查「文件存在 + 大小不为零」会放「容器头写坏但文件几百 MB」的半成品过去 ——
而那正是规格 §8 点名要防的。

## 3. 收尾（不变量 I9）

### 3.1 唯一入口，且是结构保证

`SessionFinalizer` 只有一个公开方法 `FinalizeAsync`，它**不接收**「为什么停」以外的
任何分支信息 —— `StopReason` 只被原样带进结果，**不参与任何 if**。

七种停法（手动 / 同码复扫 / 静止超时 / 时长兜底 / 孤儿收尾 / 存储将满 / 设备异常）
全部走这里。

两条测试锁住它：

- `收尾器只有一个公开入口` —— 反射断言公开方法只有 `FinalizeAsync`。
  想加旁路就必须先加一个公开方法，加不出来就是没有旁路。
- `所有停录原因走完全相同的收尾序列` —— 对每个 `StopReason` 跑一遍，
  比对实际发出的 FFmpeg 调用序列，要求逐字节相同。

### 3.2 「收尾成功」的判据包含写索引

`FinalizedSegment.IsPublished` = 产出可播成品 **且** 算过哈希 **且** 写完索引 **且** 无失败原因。

**写索引失败也算收尾失败。** 文件在盘上、哈希也对，但用户检索不到 ——
那对「找得到自己的证据」这个承诺等于没入库。

> 这一条是测试抓出来的 bug：最初的 `IsPublished` 只看 `PublishedPath` 与 `ContentHash`，
> 于是索引写失败的会话会被标成「已入库」。测试 `写索引失败不算收尾成功` 红了才发现。

### 3.3 失败时绝不删源文件

remux 失败、校验失败、索引失败 —— 任何一条失败路径都不删中间的 MKV。
那一刻它是唯一存在的副本，删了就违反 I2。

## 4. 孤儿恢复（规格 §3.1.1 / §8）

### 4.1 判据：缺 `finalized.json`

工作区目录形态：`<workRoot>/<sessionId>/session.json` + 各分段文件，
收尾成功后另写一个 `finalized.json`。

**孤儿 = 有 `session.json` 但没有 `finalized.json`。**

不用猜「文件能不能播」「进程还在不在」—— 进程被杀时来不及写任何东西，
所以「缺 finalized 标记」是唯一可靠且无需推断的信号。

`session.json` 很小，用**写临时文件再改名**保证原子性：改名之前被杀，
留下的是完整的旧版本或完整的新版本，不会有半个 JSON。

### 4.2 孤儿收尾没有自己的逻辑

`OrphanRecovery` 的全部意义就是「它没有自己的收尾逻辑」——
调的是**同一个** `SessionFinalizer`，只是 `StopReason.ProcessKilled`。

**如果哪天有人在这里加了一段「孤儿专用」的收尾代码，I9 就破了。**

### 4.3 失败重试（已知取舍）

只有成功的才打 `finalized` 标记。失败的保持孤儿身份，**下次启动重试** ——
因为源 MKV 一定还在（I2），可能只是瞬时故障。

代价：如果某个 MKV 彻底损坏，它会在每次启动时重试一遍。
换来的是「可恢复的录像不会被当成不可恢复丢掉」。
孤儿积压到影响启动时，再给 manifest 加尝试计数即可。

## 5. 存储与索引

### 5.1 归档目录布局

```
<archiveRoot>/<yyyy>/<MM>/<dd>/<单号>/<sessionId>_<序号:000>.mp4
```

按日期分层：单号检索是主路径，但规格 §3.5.2 的「保留最近 N 天」需要按时间范围
低成本列文件，目录分层比全表扫描可靠。

**进索引的只有相对路径**（规格 §6.2）。绝对路径在应用重装、容器变更后必然失效。

### 5.2 索引格式：JSON Lines

选追加写而不是重写整个文件，理由来自规格 §6.2「数据删除必须**极度克制**」：
追加写不会重写既有记录，因此不存在「重写过程中崩溃导致整库损坏」这个失败模式。

写入用信号量串行化（收尾可能在多个分段上并发发生）。

值对象（单号 / 相对路径 / 内容哈希）用的是私有构造函数，直接反序列化绕不过去，
所以单独立了一个 `RecordingEntryDto` 把「磁盘上的形状」与「内存里的类型」分开。

### 5.3 磁盘阈值

规格 §3.1.1 要求阈值由配置下发，**且必须有本地硬兜底值**。兜底值：

| 阈值 | 默认 |
|---|---|
| 警告线 | 2 GB |
| 停止线 | 512 MB |
| 收尾余量 | 512 MB |

依据：1080p H.264 约 0.5~1 MB/s，2 GB 留出约 30~60 分钟。

**收尾余量单独一项**，因为 remux 期间 MKV 与 MP4 **同时存在**。
不留的话会出现「为了安全而收尾，结果收尾到一半磁盘满了」—— 正好产出半成品，
与收尾的目的相反。

探测不了磁盘余量时**不停录**（I4 的同一条精神）：误停一个正常录制比漏报一次告警更糟。

# M3 · 检索与回放

规格 §3.8：检索维度（单号 精确/前缀/模糊、日期、发货/退货）、回放（倍速、拖拽、跳打点）、局域网网页回放。

## 7. 检索

### 7.1 「精确 / 前缀 / 模糊」对应什么

规格只给了三个词，没给语义。按中文检索界面的惯用含义对应到 SQL 形态：

| 界面用词 | 实现 | SQL 类比 |
|---|---|---|
| 精确 | 整串相等 | `= 'x'` |
| 前缀 | 以查询串开头 | `LIKE 'x%'` |
| 模糊 | 包含查询串 | `LIKE '%x%'` |

**「模糊」刻意不做到错字容忍。** 记错一位数字查不出来 —— 那是另一个功能（编辑距离或拼音），
不是「模糊查询」在中文界面里的通常含义。真要做要单独设计，不要偷偷混进这一档。

查询串本身也走归一化：用户敲小写或带空格仍能命中，因为库里的单号是大写形态。

### 7.2 规模

每次查询全量读索引文件。几千条是毫秒级，满足 M3 验收的「秒查到」。
真到十万条该换的是存储（嵌入式库或倒排索引），不是在这里加缓存 —— 提前优化会掩盖真正的瓶颈。

## 8. 标签：I5 的落点

不变量 I5：单号是唯一事实标识，公司/分类/备注都只是**可修正标签**。

**标签挂在哪**：挂在**证据**上（`EvidenceId`），不是挂在单号上。

理由：同一个单号可能既发过货又退过货。挂单号上会让两段录像共用一个「发货/退货」值，
必然有一个是错的。

**存储形态**：追加写，读取时同键后者胜出。改标签是追加一条新记录，不是原地覆盖 ——
与规格 §6.2「数据删除必须极度克制」同源：不重写既有记录，就不存在
「重写中崩溃导致整份标签损坏」这个失败模式。

**验收断言**：有一条测试专门断言「改标签不影响证据本身」——
改完标签后，证据的哈希、路径、时长必须逐字段不变。

## 9. SessionId：一个必须补上的字段

M3 开工时发现 `RecordingEntry` 里**没有 SessionId**，而「跳到打点位置」根本做不了：
打点记的是**会话内偏移**，而一次打包可能横跨多个分段文件 ——
要定位就得先把同一会话的分段归到一起。

补的方式：显式加 `SessionId` 字段。**不**靠拆 `EvidenceId` 的字符串前缀 ——
那是把编码格式当契约用，格式一改就全线崩，且没有编译期保护。

向后兼容：早期写入的记录没有这个字段，读取时退化成「自己是自己的会话」。
单段录像本来就等价于此，而它至少不会把不同会话错并到一起。

## 10. 时间轴：跨分段定位

`RecordingTimeline` 把「会话内偏移」映射到「第几段的第几秒」。

- **首尾相接无空隙**：与规格 §3.1.1「不因切分而中断用户体验」一致，连续分段录制不留空档。
- **分界点归前一段末尾**：拖到两段交界时看到上一段最后一帧，比看到下一段第一帧更符合操作直觉。
- **打点越界钳到最近一端**：打点时刻可能略晚于最后一段收尾（收尾本身要花时间），
  这时该跳到末尾让用户看到画面，而不是弹「定位失败」。
- **排序必须按会话全局偏移**，不能按段内偏移 —— 否则「第 1 段第 2 秒」会排到
  「第 0 段第 5 秒」前面。（这是写错过一次的地方，有测试锁着。）

## 11. 局域网网页回放

### 11.1 为什么用 HttpListener 而不是 ASP.NET Core

`HttpListener` 走系统自带的 http.sys，**零新依赖**，也不会给一个 WPF 桌面应用
凭空加上「必须装 ASP.NET Core 运行时」这种部署要求。

代价：Windows 上绑定通配符前缀需要一次性注册

```
netsh http add urlacl url=http://+:8720/ user=Everyone
```

这条需要管理员权限，应当由安装程序完成，别让用户自己敲。

### 11.2 绑不上时回退，而不是失败

首选 `http://+:<port>/`（局域网可达），绑不上就退到 `http://localhost:<port>/`，
并把原因变成一条**用户可见的警告**（含上面那条 netsh 命令）。

「回放服务起不来」不该让整个应用不可用 —— 收尾与录制远比回放重要（I4 的同一条精神）。

> 踩过的坑：绑定失败过的 `HttpListener` **不能复用**。`Start()` 抛异常后它内部状态
> 既不是「已启动」也不是「干净」。回退时必须用**全新实例**，不能在同一实例上
> 改 `Prefixes` 再 `Start()`。

### 11.3 路径穿越的两层防护

1. 只按**索引里的相对路径**解析，绝不拼接请求里的字符串
2. 解析完再确认落在归档根之内，挡住索引本身被污染的情况

另外 `RelativePath` 值对象本身拒绝 `..` 与绝对路径，这是第三层。

实测：带编码的 `..` 会在请求进到我们的代码**之前**被 http.sys 挡掉（403）。
所以安全测试断言的是**性质**（取不到内容）而不是具体状态码 ——
换一个 HTTP 实现状态码可能不同，但性质必须一样。

### 11.4 ⚠️ 这不是证据分享链接

本服务**直接读本机归档目录**，是给操作者自己在内网看回放用的。

规格 §3.7 的**证据分享链接**是另一回事：它由服务端签发、指向**归档层**，
因为本地副本会被生命周期清理（I7：分享链接永不指向本地副本）。

两者混用会发出一条迟早失效的链接。页面底部署名写明了这一点，且有测试断言页面里必须有这句话。

## 12. 许可独立性（L8）

许可设计 §5 / L8：试用到期 / 未激活 / 校验失败，**都不得锁住用户已有的录像** ——
历史录像必须仍可查看、检索、导出。「用户的数据是他的，不是人质。」

落点：检索与回放的所有类型**不得引用任何许可类型**。
有一条反射测试遍历这些类型的字段、构造参数、方法签名，发现许可相关类型就让测试红。

当前还没有许可实现（那是 M6），所以这条测试今天是**不会失败的** ——
它的价值是 M6 把许可接进来时的绊线。

# M2 · 摄像头采集（2026-09-22 补）

## 14. 为什么用 ffmpeg 采集，而不是 Media Foundation

本项目**已经**把 ffmpeg 当外部工具用（`FfmpegLocator`、remux、解码校验、编码探测），
采集沿用它是**零新依赖**。走 MF 要引 Windows 互操作层，还得自己接编码器 ——
而 §3.1.5 要求的编码能力探测本来就以 **ffmpeg 的编码器名**为准，
两套编码器命名混用会多出一层没有价值的映射。

## 15. 分段 = 每段一个 ffmpeg 进程

`RecordingSession` 每滚一段就起一个新 ffmpeg 进程，段满时优雅停掉它、起下一个。

| 备选 | 为什么没选 |
|---|---|
| 单进程 + segment muxer | 停录时要「封尾」，而那要求进程还活着才能协商；反而更绕 |
| 单进程 + 停录后切分 | N 分钟一段 ⇒ 崩溃时最多丢 N 分钟；逐段起进程只丢「在飞的那一段」 |

逐段起进程的代价是每段之间有约 1 秒的空档（dshow 打开设备要这么久），
所以**段的起始时间按实际起进程那一刻算**，不往前补 —— 补出来的时间是假的。

## 16. 停止必须走 stdin 的 `q`，不能杀进程树

本机实测（2026-09-22）：

| 停止方式 | 退出码 | MKV 是否完整 |
|---|---|---|
| 往 stdin 写 `q` | 0 | **完整可解** |
| `Kill(entireProcessTree: true)` | — | 丢尾部 |

所以 `FfmpegCaptureProcess` **显式重定向 stdin**（既有的 `SystemProcessRunner`
不重定向，因此不能用于采集 —— 这不是它的缺陷，它的职责是「跑完再返回」）。
强杀只作为**兜底**：`StopAsync` 等 15 秒还不退才升级为强杀，因为一个占着分片文件的
孤儿 ffmpeg 会破坏「收尾只有一条路径」（I9），那比丢尾部更糟。

## 17. 时间用单调时钟（I11 的落点）

墙钟**只在开录那一刻取一次**，之后所有时间戳都是「起点 + 单调偏移」。
用户改系统时间因此伪造不出更早的证据时间。副作用是 dshow 那 1~1.5 秒的
打开延迟不计入时间轴 —— 那段时间本来也没有画面，计进去才是错的。

## 18. manifest 必须在每段封闭时立刻落盘

孤儿判据是「有 `session.json` 但没有 `finalized.json`」，而
`RecordingWorkspace.ListOrphansAsync` **只认 manifest 里列出的分段**。
因此不写 manifest 的话，进程被杀后那批 MKV **对恢复链路完全不可见** ——
文件在盘上，但没有任何代码会去收尾它们。

开录时写第一版（分段为空），之后每封闭一段追加一次。多出的 I/O 是几 KB 的 JSON，
换来的是「任何时候被杀都能恢复」（I2）。

## 19. ⚠️ 与规格不一致的两处（需求方 2026-09-22 裁定，不是遗漏）

| # | 规格怎么说 | 实现怎么做 | 为什么 |

# 摄像头识码与帧通路（2026-09-23）

## 23. 第三方库：ZXing.Net

规格 §10 要求第三方库**逐个核对许可证**。本仓目前只有一个：

| 库 | 版本 | 许可证 | 用途 | 商用安全 |
|---|---|---|---|---|
| ZXing.Net | 0.16.10 | **Apache-2.0** | 摄像头识码（规格 §3.2.1） | 是 |

Apache-2.0 不要求衍生作品开源，无署名义务。它**不提供专利授权**这一点已知，
但一维码/二维码的读取不涉及需要授权的专利池。

选择它的另一个理由是**形状合适**：.NET 5+ 下核心包不含任何图像库绑定，
可以直接喂裸灰度像素（`RGBLuminanceSource.BitmapFormat.Gray8`），
于是不需要 ImageSharp / SkiaSharp / System.Drawing 那些重的绑定包 ——
而 ffmpeg 的 `rawvideo` + `pix_fmt gray` 输出正好是紧凑的 w×h 亮度，stride == width。

**ZXing 只出现在一个文件里**（`Camera/ZXingFrameScanner.cs`），换库只改那一处。

## 24. 帧通路：为什么不做「录制中同时识码」

原计划是让采集进程**多输出一路灰度帧**（`-map 0:v -vf fps=3,format=gray -f rawvideo pipe:1`），
这样录制中也能识码。本机实测确认**这个形状本身可行**（MKV 解码 exit=0 零错误，
裸帧尺寸分毫不差），但最终**没有采用**，理由是三条：

1. **`-t` 是输出选项**，只作用于紧跟的那一个输出；而 tap 到点会让**整个 ffmpeg 退出**，
   把还在写的 MKV 一起掐断。实测症状就是 MKV 变 0 字节或 `File ended prematurely`。
   收尾只能靠 stdin 的 `q`（见 §16）。
2. **多一路输出就多一条会堵的管道**，而堵住管道会一路顶到 ffmpeg ——
   它连 `q` 都处理不了，只能强杀，MKV 尾部就丢了（见 §16、§25）。
3. **需求方裁定的是「空闲时识码、扫到才开录」**，识码与录制**本来就不重叠**，
   双输出解决的是一个不存在的问题。

所以实际做法是：识码跑一个**独立的轻量进程**（低频、只取灰度、取够就退），
扫到单号后停掉它、再起录制进程。

## 25. 相机独占与释放（实测）

DirectShow 相机是**独占**的：录制中另起一个 ffmpeg 开同一台相机会得到
`Could not run graph ... device already in use`。

但**进程退出后设备会干净释放** —— 连开 5 次实测，5/5 成功，
每次约 1.8 秒（其中约 1.5 秒是 dshow 打开设备本身）。
所以「识码进程 → 录制进程」的交接是可行的，代价是那 1.5 秒的开机延迟。

⚠️ 这条只在本机（Lenovo EasyCamera）验过。**换摄像头要重验** ——
有些驱动在进程退出后不立刻释放句柄，那会让交接失败。

## 26. 静止检测的阈值必须真机标定

`FrameMotionDetector` 先**减均值再比**，这一步是承重的：摄像头有自动曝光与
自动白平衡，完全没人动的时候整幅画面的亮度也会缓慢漂移；
直接用绝对差比会把这种漂移当成「在动」，于是**永远判不出静止**。

`MotionOptions`（采样步长、噪声底、变化占比）是留出来的旋钮。
**默认值是猜的，不是标定出来的** —— 真机上必须按实际摄像头调。
标定时看 `MotionSample.ChangedRatio`：让画面完全静止，读它，取一个比它明显大的阈值。

## 27. 生命周期清理（规格 §3.5）：**默认什么都不清**

`RetentionPolicy` 的默认值是 `KeepAll`，这是刻意的。清理是**不可逆**的动作，
它必须是用户主动开启的 —— 不能因为「装完就有个默认 30 天」而在用户不知情时删掉东西。
规格 §6.2「数据删除必须极度克制」讲的正是这件事。

三条豁免一条都不能少（§3.5.3）：**已成功归档 / 被用户锁定 / 最近 24 小时**。
最后那条是冷静期 —— 刚录完的东西往往还在被检查、被导出。

**豁免也要出报告**（§3.5.5）：用户要能问「这条为什么被删 / 为什么没删」。
只给候选不给豁免，等于让人无从质疑。

### I8 的落点：查不了**不等于**不存在

`CleanupExecutor` 对每条候选先回查归档层，**回查不通过就绝不删除**。
这里有个必须写下来的细节：**「回查本身出错」也算不通过**。
网络断了、凭据失效的时候把结果当成「归档层上没有」，删掉的可能是**最后一份副本**（I2）。
查不了时唯一安全的动作是不删。

### 归档层是本机磁盘时**根本不删**

规格 §3.5.1：那时该副本是唯一副本。这条由 `CleanupExecutor.CanCleanup` 把关，
而不是靠调用方记得别调。界面上应当据此**根本不显示**清理选项 ——
「显示了但禁用」和「根本不显示」是两回事，后者才符合「不提供」。

### 用回收站，不直接抹

清理是不可逆的动作，多一层「还能捞回来」比省那点空间重要得多。

### ⚠️ 起算点是**归档成功时刻**，而且必须有「还没归档」这条豁免（2026-09-23 修正）

上面那句「三条豁免一条都不能少」当时是**写在文档里、没写在代码里**的。
`CleanupPlanner.Plan` 实际上只有两条（锁定、24 小时），第①条「未成功归档」缺席 ——
它只是被 I8 的回查**顺手**挡住的。两件事不一样：

- 回查说「查了，归档层上不在」；
- 豁免①说「压根没传上去，本地这份是唯一副本」。

`§3.5.4` 明说豁免与回查是**两道关**，不能拿第二道当第一道用。而且两者的
**报告文案**不同，用户看到的是「归档层上找不到这一份」，而真实原因是「还没备份」。

同一个方法还有第二处错，方向更隐蔽：**保留期用的是 `entry.EndedAt`（录完时刻）**。
规格 §3.5.2.1 要求自**归档成功时刻**起算，依据是 §4.3 的合取式
「归档成功 **且** 超过保留期」—— 一台离线 35 天的机器若按录完时刻算，
会在**刚归档那一瞬间**就被删掉，那等于绕开了「至少一份副本」（I2）的意图。
§9 的验收判据原文就是「离线 35 天后才归档的段，**归档当天不算已过期**」。
现在用回执里的 `TimeAnchor`。

`Plan` / `PlanPerBusinessType` 因此多一个**必填**参数 `archiveAnchors`
（`evidenceId → 归档成功时刻`），表里没有某个 id 就是「还没归档」。
必填是刻意的：默认值会让「忘了传归档状态」变成一种合法输入，
而它正好会删掉唯一副本。手机端 `lifecycle.dart` 的 `planCleanup` 也是必填，
两端同一个理由、同一套口径（三条豁免的顺序也按 §3.5.3 自己的编号）。

⚠️ **谁来提供那份归档时刻表，目前还没有答案。** 回执里就有
（`ReceiptPayload.TimeAnchor`），但 `ReceiptStore` 只有按 id 查一个的 `FindAsync`，
没有「一次读全表」。要接上的第一步是给它加 `LoadAllAsync` ——
**现在故意不加**：在本类有生产调用点之前，那会是一段没人调用、也没法验证的代码
（正是本仓 §28 那种「写完了、测过了、没插电」）。

### 已知：一个间歇性失败的测试

`DesktopServicesTests.端到端_启动时收尾上次没走完的会话` 约 **1/7 概率**失败，
连跑 6 次全过、单跑必过。根因大概率是 `FreePort()` 的「关了再还」写法：
它 `Stop()` 掉探测用的监听再返回端口号，而别的测试可能在这中间抢到同一个端口。
**这是既有问题，与本次清理功能无关**，但没修 —— 修它要改成「一直持有到绑定时刻」，
那会牵动 PlaybackServer 的装配方式。先记在这里。

# 装配与接线（2026-09-23）

## 28. 装配的最后一跳

一次盘点查出**三处「写完了、测过了、没插电」**，全都落在组合根上：
功能代码在 Core 里、各自的测试全绿，而把零件接起来的那几步在 App 层、
或者根本没有被任何人调用。它们有一个共同点：**失效的表现全都是「没反应」**。

### 28.1 回放服务与孤儿收尾从没启动过

`DesktopServices.Create` 与 `DesktopServices.StartAsync` 是**两个**方法，
而 `AppHost.StartAsync` 只调了前者。三个功能因此静默失效：

- 收尾上次没走完的孤儿（规格 §3.1.1）—— 那段录像既不进索引也播不了；
- 回放服务（M3 的验收项）—— 网页回放**从来没有起来过**；
- 主窗口的「局域网回放页」按钮 —— 它读 `Server.BaseUrl`，那个值只在 `StartAsync`
  里才有 ⇒ **永久禁用**。

而 `README.md` 与窗口上的文案都按「会起」来写（「启动即用：应用会先收尾上次
没走完的录像，再起回放服务」）。这正是 `IMPLEMENTATION.md` §384 说的
「看起来完成了」。

### 28.2 编排循环从没被启动（最严重的一处）

`RecordingSession.RunAsync` 里那个循环负责**滚段**（§3.1.1）、**时长兜底**（§3.3.4）
与**磁盘将满主动收尾**。它在 `src` 里**一个调用点都没有** —— 协调器只调
`StartAsync` 起了第一个分段就结束了。后果不是「档位不生效」那么小：

- 整场只录一个**永不滚动**的分段。段不滚 ⇒ manifest 里一段都没封闭
  ⇒ 进程被杀后**什么都恢复不出来** —— 而滚段存在的理由正是这个。
- 时长兜底永不触发；磁盘将满也不会主动收尾。
- 「分段时长」「时长兜底」两个档位改起来毫无反应，根子在这里。

会话层对此**测得很透**（`RecordingSessionTests` 里一批 `FakeClock` + `AdvancingDelay`
用例，滚段、时长兜底、磁盘将满、编排异常全都覆盖），坏的只是没人起这个循环 ——
所以它躲过了整套 340 条测试。

现在协调器起循环，并用一次 `Interlocked.CompareExchange` **认领**
「这次收尾是我主动发起的，还是循环自己停的」：循环自己收尾时必须把它接回来，
否则 `_current` 会一直指着那个已经收尾的会话 —— 界面停在「录制中」，
用户会一直等一个永远不会发生的停录，也就不会去点【结束】。

### 28.3 三个档位只写不读

`AppSettings.SegmentMinutes` / `DurationFallback` / `StaticStop` 有界面、有落盘、
有变更日志，**没有任何读者**。现在：

- 前两个经 `RecordingSessionOptions.From` 送到会话 —— 映射**只此一处**，
  写两遍早晚会不一致，而不一致的表现是「界面上写着 5 分钟、实际按 1 分钟录」，
  极难被发现。越界值**夹回合法区间**而不是抛：设置文件是可以被手改的，
  一个改坏了的配置不该让用户录不了像（I4 的同一条精神）。
- `WorkModePolicy` 的 `Mode` / `StaticStop` 从 readonly 字段改成**可写属性**，
  由协调器写穿。设置页那句「工作模式立即生效」从此是真的 ——
  在此之前它只在重启后成立。

「时长兜底 = 关闭」用 `TimeSpan.MaxValue` 表示「永远比不到」，而不是把它改成可空：
循环里只有一次比较，没有任何算术，所以不必为此加分支和一圈可空判断。

### 28.4 ⚠️ 这一批靠一条**文字绊线**挡回归，它的天花板要说清楚

`AppHost` 在 `VidLog.Desktop.App`（WPF、`net9.0-windows`），而测试工程是 `net9.0`，
**引用不了**；App 层也没有自己的测试工程。所以「组合根少调了一步」这类 bug
对整套测试**完全不可见** —— 28.1 就是这么漏过去的。

挡它的是 `DesktopServicesTests.AppHost_装配时会真的启动服务`：它读 `AppHost.cs`
的源码文本，断言那句调用还在。**这不是行为测试**，是这个项目已经用过的绊线手法
（另一条是许可独立性那条「今天是不会失败的」测试）。

天花板：它只挡「这一行被删了/被注释了」，挡不住「改成一个不跑的路径」。
**根治**有两条路，哪条都比绊线强：

1. 给 App 层一个 `net9.0-windows` 测试工程；
2. 把 `DesktopServices.Create` 与 `StartAsync` 合成一个**忘不掉**的方法
   （唯一入口 ⇒ 拿不到「未启动」的实例 ⇒ 这一步在类型上做不到忘记）。

那时这条绊线应当删掉。

⚠️ 还有一个坑值得记下来：绊线的第一版只断言「源码里有这串文本」，
而 `// await services.StartAsync(...)` 里**仍然含有**这串文本 ——
于是「把调用注释掉」这个最常见的失活方式反而抓不住。第二版改成逐行检查、
排除以 `//` 开头的行。

### 28.5 静止停录仍然做不了，而且原因不是「没时间」

它要的是**录制中拿到画面**，而那条路 §24 已经用实测否决过：多一路输出就多一条
会堵的管道，而堵住管道会一路顶到 ffmpeg —— 它连 `q` 都处理不了，只能强杀，
正在写的 MKV 尾部就丢了。另起一个取帧进程也不行：DirectShow 相机是**独占**的（§25）。

所以设置页那个下拉现在**如实写着它不生效**（踩坑 #13：一个改了没反应的开关，
用户只会以为它坏了），连「扫码静止停录」那个工作模式一起 —— 后者的静止判据
同样取不到输入。

要接上的候选路子是**取样正在写的那个 MKV 文件**：第二路只读文件、不碰相机，
绕开独占，也绕开管道拖垮录制。但它的可行性、以及对「写入中的 MKV」的读取行为
（索引还没写完），**必须真机 + 真 ffmpeg 验** —— 本机两样都没有。
所以这条**留作待办，不猜一个实现**：`FrameMotionDetector` 与
`MotionOptions` 的阈值本来就是「纸面推导、必须真机标定」（§26），
再叠一层没验过的取帧路径，等于把两件不确定的事焊在一起。

# 入网：二维码连接（规格 §3.4.5）

2026-09-24 决定：**6 位配对码由二维码取代**。二维码里只放两样东西 ——
电脑端的**可达地址**与**一次性短时效令牌**，**绝不含凭据**；
凭据只在 `claim` 那一步发放，且只发一次。

「必须站在主机屏幕前」这个前提**一个字都没放松**：码显示在电脑端屏幕上，
扫不到就进不来。令牌仍是**明文走在局域网里**的（与原来的 6 位码一样），
所以这一层挡的是「不在屏幕前的人」，**不挡**同在局域网里抓包的人 ——
不要误以为二维码更安全。

## 29. 电脑端界面那半（2026-09-26）

### 29.1 为什么单独开一个窗，而且是模态

塞不进主窗口：这张码要能被手机清楚地扫到，得占 280px 见方，旁边还不能堆控件
（主窗口密密麻麻）。

**模态**是为了「一次只有一张码」—— `DeviceRegistry` 只留得住**最后一张** session。
屏幕上摆着两张、能用的只有一张，那是最难解释的一种「扫了没反应」。

### 29.2 「同意 / 拒绝」的默认按钮必须是「否」

`MessageBox.Show(..., MessageBoxResult.No)`。默认落在「是」的话，回车、
或者随手关掉弹窗（许多人的肌肉记忆里，关掉 = 消掉这个提示）**都等于批准**，
而批准之后那台设备就能把录像传进来。这里宁可让人多按一下。

批准过 / 拒绝过的设备记在 `_asked` 里：同一条请求不再弹第二次。
**拒绝之后那条请求不清掉**（清了手机会看到「重新扫码」，而它只是等了一个「不」），
它下一轮轮询拿到的就是同一个答复。

### 29.3 发不出码时**绝不显示一张假的**

四种机器状态各自有话说：没装配回放服务 / 服务没起来 / 只绑到了本机（缺 urlacl）/
挑不到局域网地址。一律不画码，红字写清原因**和怎么才能好**。
少了后一句，用户看到的是一张扫不动的码 —— 而他会以为是手机的问题。

### 29.4 两处静默的坏法

- **心跳必须在轮询之前点**：`_ticker.Start()` 写在 `await PollAsync()` **后面**的话，
  `PollAsync` 里万一走到 `Expire()`（它停掉心跳），紧接着那一句又把它打开，
  从此**再没有人停它** —— 码已经失效了，倒计时却还在跳。
- **`_busy` 挡轮询重入**：WPF 的模态弹窗跑一个嵌套消息循环，
  `DispatcherTimer` 在里面**照样触发**，没有守卫的话一轮申请能弹出一串一模一样的窗。

设备列表每秒都被刷一遍，内容没变就不重设 `ItemsSource`（重设会重建整个列表，
用户正在看的那一行会跳一下）。

### 29.5 「深色是 0 还是 255」收口到 `EnrollQr.Pixels`

这个约定原先有**两份**：一份在测试脚手架的像素循环里，一份在界面层 ——
而**界面那份没人看**（测试抄得再对，屏幕上那份写反了照样是绿的）。

现在字节由 Core 的 `EnrollQr.Pixels` 摊，界面只负责放大
（`PixelFormats.Gray8` + `NearestNeighbor`），于是往返测试证明的是
「**画到屏幕上的那些字节**解得回原串」。用 `Gray8` 而不是 `BlackWhite`：
后者按位打包，"0 是黑还是白"得再看一次文档。

写反的表现是**一张反色码**：有静区、有方阵、比例也对，看着完全正常，**扫不出来**。
轴序写错则表现为**整体转置**，同样是合法图形，同样扫不出来。两种都只有拿手机去扫才知道。

### 29.6 ⚠️ 第二条件线，天花板与 §28.4 逐字相同

App 层没有测试工程 ⇒ 「界面上到底有没有地方能显示出那张码」对整套测试**不可见**，
而这件事**真的发生过**：2026-09-24 收工时 `PendingAsync` 与 `DevicesAsync` 是
**零调用点** —— Core 逻辑、单测、CI 全绿，屏幕上却没有地方显示二维码
⇒ 手机永远换不到凭据 ⇒ **M5 端到端走不通**。那不是「没联过」，是这一步根本没做。

挡它的是 `DesktopServicesTests.入网二维码在界面上真的有出路`：读四个文件的源码文本，
断言 `OpenSessionAsync(` / `PendingAsync(` / `DecideAsync(` / `new EnrollWindow(` 都还在。

天花板：只挡「有人把这一行删了 / 注释了」，挡不住「改成一个不跑的路径」。
根治同样是把 App 层做成可测的（见 §28.4 那两条路）；那时这条绊线应当删掉。

⚠️ 写这条时踩到的坑值得记下来：第一版的剥注释只删掉 `TrimStart()` 以 `//`
**开头**的行，于是**行尾内联注释**里的片段仍然留在文本里 ——
把调用改成 `var decided = true; // await ...DecideAsync(...)`，测试**照常绿**。
必须真正把片段删掉才红得起来。

### 29.7 手机端那半**还没做**（两端现在对不上）

`lib/upload/uploader.dart` 的 `enrollClaim({deviceId, code})` 仍然要一个**手输的 6 位码**，
而电脑端已经在发二维码 + 令牌。做手机端那半时要把它换成令牌，
并顺手删掉手机端 `README.md` 里说明这件事的那一段。

本机也没有摄像头，`AppHost` 在没有 ffmpeg 时直接抛。
