## 1. 扫码枪判定（规格 §3.2.1）

判定规则是「**短时间内的连续按键 + 结束符**」，规格没给具体数值。

| 参数 | 取值 | 依据 |
|---|---|---|
| 相邻按键最大间隔 | **50 ms** | USB HID 扫码枪通常 1~10 ms/键，偶尔到 30 ms；人类打字再快也在 80 ms 以上 |
| 最短长度 | 5 | 太短的串不可能是单号 |
| 最长长度 | 40 | 超过即误触 |
| 结束符 | `\r` `\n` `\t` | 扫码枪普遍发 Enter |

**「不能吞掉用户正常打字」靠三层保证**：

1. 间隔超阈值 → 判定为人类输入，整串放弃
2. 串里出现单号不可能有的字符（空格、`/`、`@`、中文……）→ 放弃
3. 长度越界 → 放弃

人类要以 50 ms 以内的间隔敲出 5 个以上合法单号字符再按回车，实际上不可能。

### 1.1 键盘自动重复（实现中发现，规格没提）

**按住某键不放时，Windows 的自动重复间隔约 30 ms —— 落在 50 ms 阈值之内。**
所以在「按住一个字母键 + 敲回车」的场景下，会被误判成一次扫码。

防护：**整串字符完全相同就放弃**。自动重复必产生一串相同字符，而真实单号极少全同。
代价是形如 `000000000000` 的单号会漏判 —— 极罕见，且漏判只退化成手动输入，
不会误吞用户输入。

> 判定逻辑做成对按键流的**纯函数**（`ScannerKeystrokeDetector`），不接触键盘、不吞按键。
> 接触键盘的是平台层（Windows 全局钩子），那是投递，不是判定 —— 分开才能把
> 「阈值、边界、误判」这些最容易错的部分完整测到。

## 2. 录像链路（规格 §3.1.4 / §3.1.5）

### 2.1 为什么录制期写 MKV、停下来再 remux 成 MP4

MP4 的索引（`moov`）在**文件末尾**。进程被杀时那段没写下去，整个文件就是彻底打不开的废件
—— 正好撞上规格 §8 的「录制中掉电/进程被杀」和 I9 的「不产生无法播放的半成品」。

MKV 是分段结构，写到哪算哪，剩余的也能解出来。

所以：**录制期 MKV 中间容器 → 停止后 `-c copy` 无损 remux → MP4 成品**。
`-c copy` 不重编码，画面零损失，也快。加了 `-movflags +faststart` 把 moov 挪到文件头。

### 2.2 编码能力必须实测，不能查表

`ffmpeg -encoders` 列出的是「**编译进去了**」，不是「**这台机器能跑**」。

本机实测（2026-09-16）：

| 编码器 | 列表里 | 实测 |
|---|---|---|
| `libx264` / `libx265` / `h264_qsv` | 有 | ✅ 能出片 |
| `h264_nvenc` | 有 | ❌ 无 NVIDIA 卡 |
| `h264_amf` | 有 | ❌ 无 AMD 卡 |
| `hevc_qsv` | 有 | ❌ HD 630 上 qsv 编不了 HEVC |

**8 个里只有 3 个真能用。** 所以 `FfmpegEncoderProbe` 是**真编一小段再解码验一遍**。

另外注意：失败退出码五花八门（实测见过 `-1`、`-1313558101`、`-40`），
而且**退出码为 0 也可能是空产物** —— 所以判据是「产物存在 + 非空 + 真能解码」，
不是「退出码等于 0」。

候选顺序：`h264_nvenc` → `h264_qsv` → `h264_amf` → `libx264`（硬件优先，软件兜底）。
取第一个**实测可用**的。

### 2.3 成品校验是「真解一遍」

`DecodeVerifier` 跑 `ffmpeg -v error -i <成品> -f null -`，判据两条：

1. 退出码为 0
2. **stderr 为空**

第二条不能省：FFmpeg 遇到损坏的流常常**照样退 0**，只是往 stderr 里骂。
只检查「文件存在 + 大小不为零」会放「容器头写坏但文件几百 MB」的半成品过去 ——
而那正是规格 §8 点名要防的。

## 3. 收尾（不变量 I9）

### 3.1 唯一入口，且是结构保证

`SessionFinalizer` 只有一个公开方法 `FinalizeAsync`，它**不接收**「为什么停」以外的
任何分支信息 —— `StopReason` 只被原样带进结果，**不参与任何 if**。

七种停法（手动 / 同码复扫 / 静止超时 / 时长兜底 / 孤儿收尾 / 存储将满 / 设备异常）
全部走这里。

两条测试锁住它：

- `收尾器只有一个公开入口` —— 反射断言公开方法只有 `FinalizeAsync`。
  想加旁路就必须先加一个公开方法，加不出来就是没有旁路。
- `所有停录原因走完全相同的收尾序列` —— 对每个 `StopReason` 跑一遍，
  比对实际发出的 FFmpeg 调用序列，要求逐字节相同。

### 3.2 「收尾成功」的判据包含写索引

`FinalizedSegment.IsPublished` = 产出可播成品 **且** 算过哈希 **且** 写完索引 **且** 无失败原因。

**写索引失败也算收尾失败。** 文件在盘上、哈希也对，但用户检索不到 ——
那对「找得到自己的证据」这个承诺等于没入库。

> 这一条是测试抓出来的 bug：最初的 `IsPublished` 只看 `PublishedPath` 与 `ContentHash`，
> 于是索引写失败的会话会被标成「已入库」。测试 `写索引失败不算收尾成功` 红了才发现。

### 3.3 失败时绝不删源文件

remux 失败、校验失败、索引失败 —— 任何一条失败路径都不删中间的 MKV。
那一刻它是唯一存在的副本，删了就违反 I2。

## 4. 孤儿恢复（规格 §3.1.1 / §8）

### 4.1 判据：缺 `finalized.json`

工作区目录形态：`<workRoot>/<sessionId>/session.json` + 各分段文件，
收尾成功后另写一个 `finalized.json`。

**孤儿 = 有 `session.json` 但没有 `finalized.json`。**

不用猜「文件能不能播」「进程还在不在」—— 进程被杀时来不及写任何东西，
所以「缺 finalized 标记」是唯一可靠且无需推断的信号。

`session.json` 很小，用**写临时文件再改名**保证原子性：改名之前被杀，
留下的是完整的旧版本或完整的新版本，不会有半个 JSON。

### 4.2 孤儿收尾没有自己的逻辑

`OrphanRecovery` 的全部意义就是「它没有自己的收尾逻辑」——
调的是**同一个** `SessionFinalizer`，只是 `StopReason.ProcessKilled`。

**如果哪天有人在这里加了一段「孤儿专用」的收尾代码，I9 就破了。**

### 4.3 失败重试（已知取舍）

只有成功的才打 `finalized` 标记。失败的保持孤儿身份，**下次启动重试** ——
因为源 MKV 一定还在（I2），可能只是瞬时故障。

代价：如果某个 MKV 彻底损坏，它会在每次启动时重试一遍。
换来的是「可恢复的录像不会被当成不可恢复丢掉」。
孤儿积压到影响启动时，再给 manifest 加尝试计数即可。

## 5. 存储与索引

### 5.1 归档目录布局

```
<archiveRoot>/<yyyy>/<MM>/<dd>/<单号>/<sessionId>_<序号:000>.mp4
```

按日期分层：单号检索是主路径，但规格 §3.5.2 的「保留最近 N 天」需要按时间范围
低成本列文件，目录分层比全表扫描可靠。

**进索引的只有相对路径**（规格 §6.2）。绝对路径在应用重装、容器变更后必然失效。

### 5.2 索引格式：JSON Lines

选追加写而不是重写整个文件，理由来自规格 §6.2「数据删除必须**极度克制**」：
追加写不会重写既有记录，因此不存在「重写过程中崩溃导致整库损坏」这个失败模式。

写入用信号量串行化（收尾可能在多个分段上并发发生）。

值对象（单号 / 相对路径 / 内容哈希）用的是私有构造函数，直接反序列化绕不过去，
所以单独立了一个 `RecordingEntryDto` 把「磁盘上的形状」与「内存里的类型」分开。

### 5.3 磁盘阈值

规格 §3.1.1 要求阈值由配置下发，**且必须有本地硬兜底值**。兜底值：

| 阈值 | 默认 |
|---|---|
| 警告线 | 2 GB |
| 停止线 | 512 MB |
| 收尾余量 | 512 MB |

依据：1080p H.264 约 0.5~1 MB/s，2 GB 留出约 30~60 分钟。

**收尾余量单独一项**，因为 remux 期间 MKV 与 MP4 **同时存在**。
不留的话会出现「为了安全而收尾，结果收尾到一半磁盘满了」—— 正好产出半成品，
与收尾的目的相反。

探测不了磁盘余量时**不停录**（I4 的同一条精神）：误停一个正常录制比漏报一次告警更糟。

# M3 · 检索与回放

规格 §3.8：检索维度（单号 精确/前缀/模糊、日期、发货/退货）、回放（倍速、拖拽、跳打点）、局域网网页回放。

## 7. 检索

### 7.1 「精确 / 前缀 / 模糊」对应什么

规格只给了三个词，没给语义。按中文检索界面的惯用含义对应到 SQL 形态：

| 界面用词 | 实现 | SQL 类比 |
|---|---|---|
| 精确 | 整串相等 | `= 'x'` |
| 前缀 | 以查询串开头 | `LIKE 'x%'` |
| 模糊 | 包含查询串 | `LIKE '%x%'` |

**「模糊」刻意不做到错字容忍。** 记错一位数字查不出来 —— 那是另一个功能（编辑距离或拼音），
不是「模糊查询」在中文界面里的通常含义。真要做要单独设计，不要偷偷混进这一档。

查询串本身也走归一化：用户敲小写或带空格仍能命中，因为库里的单号是大写形态。

### 7.2 规模

每次查询全量读索引文件。几千条是毫秒级，满足 M3 验收的「秒查到」。
真到十万条该换的是存储（嵌入式库或倒排索引），不是在这里加缓存 —— 提前优化会掩盖真正的瓶颈。

## 8. 标签：I5 的落点

不变量 I5：单号是唯一事实标识，公司/分类/备注都只是**可修正标签**。

**标签挂在哪**：挂在**证据**上（`EvidenceId`），不是挂在单号上。

理由：同一个单号可能既发过货又退过货。挂单号上会让两段录像共用一个「发货/退货」值，
必然有一个是错的。

**存储形态**：追加写，读取时同键后者胜出。改标签是追加一条新记录，不是原地覆盖 ——
与规格 §6.2「数据删除必须极度克制」同源：不重写既有记录，就不存在
「重写中崩溃导致整份标签损坏」这个失败模式。

**验收断言**：有一条测试专门断言「改标签不影响证据本身」——
改完标签后，证据的哈希、路径、时长必须逐字段不变。

## 9. SessionId：一个必须补上的字段

M3 开工时发现 `RecordingEntry` 里**没有 SessionId**，而「跳到打点位置」根本做不了：
打点记的是**会话内偏移**，而一次打包可能横跨多个分段文件 ——
要定位就得先把同一会话的分段归到一起。

补的方式：显式加 `SessionId` 字段。**不**靠拆 `EvidenceId` 的字符串前缀 ——
那是把编码格式当契约用，格式一改就全线崩，且没有编译期保护。

向后兼容：早期写入的记录没有这个字段，读取时退化成「自己是自己的会话」。
单段录像本来就等价于此，而它至少不会把不同会话错并到一起。

## 10. 时间轴：跨分段定位

`RecordingTimeline` 把「会话内偏移」映射到「第几段的第几秒」。

- **首尾相接无空隙**：与规格 §3.1.1「不因切分而中断用户体验」一致，连续分段录制不留空档。
- **分界点归前一段末尾**：拖到两段交界时看到上一段最后一帧，比看到下一段第一帧更符合操作直觉。
- **打点越界钳到最近一端**：打点时刻可能略晚于最后一段收尾（收尾本身要花时间），
  这时该跳到末尾让用户看到画面，而不是弹「定位失败」。
- **排序必须按会话全局偏移**，不能按段内偏移 —— 否则「第 1 段第 2 秒」会排到
  「第 0 段第 5 秒」前面。（这是写错过一次的地方，有测试锁着。）

## 11. 局域网网页回放

### 11.1 为什么用 HttpListener 而不是 ASP.NET Core

`HttpListener` 走系统自带的 http.sys，**零新依赖**，也不会给一个 WPF 桌面应用
凭空加上「必须装 ASP.NET Core 运行时」这种部署要求。

代价：Windows 上绑定通配符前缀需要一次性注册

```
netsh http add urlacl url=http://+:8720/ user=Everyone
```

这条需要管理员权限，应当由安装程序完成，别让用户自己敲。

### 11.2 绑不上时回退，而不是失败

首选 `http://+:<port>/`（局域网可达），绑不上就退到 `http://localhost:<port>/`，
并把原因变成一条**用户可见的警告**（含上面那条 netsh 命令）。

「回放服务起不来」不该让整个应用不可用 —— 收尾与录制远比回放重要（I4 的同一条精神）。

> 踩过的坑：绑定失败过的 `HttpListener` **不能复用**。`Start()` 抛异常后它内部状态
> 既不是「已启动」也不是「干净」。回退时必须用**全新实例**，不能在同一实例上
> 改 `Prefixes` 再 `Start()`。

### 11.3 路径穿越的两层防护

1. 只按**索引里的相对路径**解析，绝不拼接请求里的字符串
2. 解析完再确认落在归档根之内，挡住索引本身被污染的情况

另外 `RelativePath` 值对象本身拒绝 `..` 与绝对路径，这是第三层。

实测：带编码的 `..` 会在请求进到我们的代码**之前**被 http.sys 挡掉（403）。
所以安全测试断言的是**性质**（取不到内容）而不是具体状态码 ——
换一个 HTTP 实现状态码可能不同，但性质必须一样。

### 11.4 ⚠️ 这不是证据分享链接

本服务**直接读本机归档目录**，是给操作者自己在内网看回放用的。

规格 §3.7 的**证据分享链接**是另一回事：它由服务端签发、指向**归档层**，
因为本地副本会被生命周期清理（I7：分享链接永不指向本地副本）。

两者混用会发出一条迟早失效的链接。页面底部署名写明了这一点，且有测试断言页面里必须有这句话。

## 12. 许可独立性（L8）

许可设计 §5 / L8：试用到期 / 未激活 / 校验失败，**都不得锁住用户已有的录像** ——
历史录像必须仍可查看、检索、导出。「用户的数据是他的，不是人质。」

落点：检索与回放的所有类型**不得引用任何许可类型**。
有一条反射测试遍历这些类型的字段、构造参数、方法签名，发现许可相关类型就让测试红。

当前还没有许可实现（那是 M6），所以这条测试今天是**不会失败的** ——
它的价值是 M6 把许可接进来时的绊线。

# M2 · 摄像头采集（2026-09-22 补）

## 14. 为什么用 ffmpeg 采集，而不是 Media Foundation

本项目**已经**把 ffmpeg 当外部工具用（`FfmpegLocator`、remux、解码校验、编码探测），
采集沿用它是**零新依赖**。走 MF 要引 Windows 互操作层，还得自己接编码器 ——
而 §3.1.5 要求的编码能力探测本来就以 **ffmpeg 的编码器名**为准，
两套编码器命名混用会多出一层没有价值的映射。

## 15. 分段 = 每段一个 ffmpeg 进程

`RecordingSession` 每滚一段就起一个新 ffmpeg 进程，段满时优雅停掉它、起下一个。

| 备选 | 为什么没选 |
|---|---|
| 单进程 + segment muxer | 停录时要「封尾」，而那要求进程还活着才能协商；反而更绕 |
| 单进程 + 停录后切分 | N 分钟一段 ⇒ 崩溃时最多丢 N 分钟；逐段起进程只丢「在飞的那一段」 |

逐段起进程的代价是每段之间有约 1 秒的空档（dshow 打开设备要这么久），
所以**段的起始时间按实际起进程那一刻算**，不往前补 —— 补出来的时间是假的。

## 16. 停止必须走 stdin 的 `q`，不能杀进程树

本机实测（2026-09-22）：

| 停止方式 | 退出码 | MKV 是否完整 |
|---|---|---|
| 往 stdin 写 `q` | 0 | **完整可解** |
| `Kill(entireProcessTree: true)` | — | 丢尾部 |

所以 `FfmpegCaptureProcess` **显式重定向 stdin**（既有的 `SystemProcessRunner`
不重定向，因此不能用于采集 —— 这不是它的缺陷，它的职责是「跑完再返回」）。
强杀只作为**兜底**：`StopAsync` 等 15 秒还不退才升级为强杀，因为一个占着分片文件的
孤儿 ffmpeg 会破坏「收尾只有一条路径」（I9），那比丢尾部更糟。

## 17. 时间用单调时钟（I11 的落点）

墙钟**只在开录那一刻取一次**，之后所有时间戳都是「起点 + 单调偏移」。
用户改系统时间因此伪造不出更早的证据时间。副作用是 dshow 那 1~1.5 秒的
打开延迟不计入时间轴 —— 那段时间本来也没有画面，计进去才是错的。

## 18. manifest 必须在每段封闭时立刻落盘

孤儿判据是「有 `session.json` 但没有 `finalized.json`」，而
`RecordingWorkspace.ListOrphansAsync` **只认 manifest 里列出的分段**。
因此不写 manifest 的话，进程被杀后那批 MKV **对恢复链路完全不可见** ——
文件在盘上，但没有任何代码会去收尾它们。

开录时写第一版（分段为空），之后每封闭一段追加一次。多出的 I/O 是几 KB 的 JSON，
换来的是「任何时候被杀都能恢复」（I2）。

## 19. ⚠️ 与规格不一致的两处（需求方 2026-09-22 裁定，不是遗漏）

| # | 规格怎么说 | 实现怎么做 | 为什么 |

# 摄像头识码与帧通路（2026-09-23）

## 23. 第三方库：ZXing.Net

规格 §10 要求第三方库**逐个核对许可证**。本仓目前只有一个：

| 库 | 版本 | 许可证 | 用途 | 商用安全 |
|---|---|---|---|---|
| ZXing.Net | 0.16.10 | **Apache-2.0** | 摄像头识码（规格 §3.2.1） | 是 |

Apache-2.0 不要求衍生作品开源，无署名义务。它**不提供专利授权**这一点已知，
但一维码/二维码的读取不涉及需要授权的专利池。

选择它的另一个理由是**形状合适**：.NET 5+ 下核心包不含任何图像库绑定，
可以直接喂裸灰度像素（`RGBLuminanceSource.BitmapFormat.Gray8`），
于是不需要 ImageSharp / SkiaSharp / System.Drawing 那些重的绑定包 ——
而 ffmpeg 的 `rawvideo` + `pix_fmt gray` 输出正好是紧凑的 w×h 亮度，stride == width。

**ZXing 只出现在一个文件里**（`Camera/ZXingFrameScanner.cs`），换库只改那一处。

## 24. 帧通路：为什么不做「录制中同时识码」

原计划是让采集进程**多输出一路灰度帧**（`-map 0:v -vf fps=3,format=gray -f rawvideo pipe:1`），
这样录制中也能识码。本机实测确认**这个形状本身可行**（MKV 解码 exit=0 零错误，
裸帧尺寸分毫不差），但最终**没有采用**，理由是三条：

1. **`-t` 是输出选项**，只作用于紧跟的那一个输出；而 tap 到点会让**整个 ffmpeg 退出**，
   把还在写的 MKV 一起掐断。实测症状就是 MKV 变 0 字节或 `File ended prematurely`。
   收尾只能靠 stdin 的 `q`（见 §16）。
2. **多一路输出就多一条会堵的管道**，而堵住管道会一路顶到 ffmpeg ——
   它连 `q` 都处理不了，只能强杀，MKV 尾部就丢了（见 §16、§25）。
3. **需求方裁定的是「空闲时识码、扫到才开录」**，识码与录制**本来就不重叠**，
   双输出解决的是一个不存在的问题。

所以实际做法是：识码跑一个**独立的轻量进程**（低频、只取灰度、取够就退），
扫到单号后停掉它、再起录制进程。

## 25. 相机独占与释放（实测）

DirectShow 相机是**独占**的：录制中另起一个 ffmpeg 开同一台相机会得到
`Could not run graph ... device already in use`。

但**进程退出后设备会干净释放** —— 连开 5 次实测，5/5 成功，
每次约 1.8 秒（其中约 1.5 秒是 dshow 打开设备本身）。
所以「识码进程 → 录制进程」的交接是可行的，代价是那 1.5 秒的开机延迟。

⚠️ 这条只在本机（Lenovo EasyCamera）验过。**换摄像头要重验** ——
有些驱动在进程退出后不立刻释放句柄，那会让交接失败。

## 26. 静止检测的阈值必须真机标定

`FrameMotionDetector` 先**减均值再比**，这一步是承重的：摄像头有自动曝光与
自动白平衡，完全没人动的时候整幅画面的亮度也会缓慢漂移；
直接用绝对差比会把这种漂移当成「在动」，于是**永远判不出静止**。

`MotionOptions`（采样步长、噪声底、变化占比）是留出来的旋钮。
**默认值是猜的，不是标定出来的** —— 真机上必须按实际摄像头调。
标定时看 `MotionSample.ChangedRatio`：让画面完全静止，读它，取一个比它明显大的阈值。

## 27. 生命周期清理（规格 §3.5）：**默认什么都不清**

`RetentionPolicy` 的默认值是 `KeepAll`，这是刻意的。清理是**不可逆**的动作，
它必须是用户主动开启的 —— 不能因为「装完就有个默认 30 天」而在用户不知情时删掉东西。
规格 §6.2「数据删除必须极度克制」讲的正是这件事。

三条豁免一条都不能少（§3.5.3）：**已成功归档 / 被用户锁定 / 最近 24 小时**。
最后那条是冷静期 —— 刚录完的东西往往还在被检查、被导出。

**豁免也要出报告**（§3.5.5）：用户要能问「这条为什么被删 / 为什么没删」。
只给候选不给豁免，等于让人无从质疑。

### I8 的落点：查不了**不等于**不存在

`CleanupExecutor` 对每条候选先回查归档层，**回查不通过就绝不删除**。
这里有个必须写下来的细节：**「回查本身出错」也算不通过**。
网络断了、凭据失效的时候把结果当成「归档层上没有」，删掉的可能是**最后一份副本**（I2）。
查不了时唯一安全的动作是不删。

### 归档层是本机磁盘时**根本不删**

规格 §3.5.1：那时该副本是唯一副本。这条由 `CleanupExecutor.CanCleanup` 把关，
而不是靠调用方记得别调。界面上应当据此**根本不显示**清理选项 ——
「显示了但禁用」和「根本不显示」是两回事，后者才符合「不提供」。

### 用回收站，不直接抹

清理是不可逆的动作，多一层「还能捞回来」比省那点空间重要得多。

### ⚠️ 起算点是**归档成功时刻**，而且必须有「还没归档」这条豁免（2026-09-23 修正）

上面那句「三条豁免一条都不能少」当时是**写在文档里、没写在代码里**的。
`CleanupPlanner.Plan` 实际上只有两条（锁定、24 小时），第①条「未成功归档」缺席 ——
它只是被 I8 的回查**顺手**挡住的。两件事不一样：

- 回查说「查了，归档层上不在」；
- 豁免①说「压根没传上去，本地这份是唯一副本」。

`§3.5.4` 明说豁免与回查是**两道关**，不能拿第二道当第一道用。而且两者的
**报告文案**不同，用户看到的是「归档层上找不到这一份」，而真实原因是「还没备份」。

同一个方法还有第二处错，方向更隐蔽：**保留期用的是 `entry.EndedAt`（录完时刻）**。
规格 §3.5.2.1 要求自**归档成功时刻**起算，依据是 §4.3 的合取式
「归档成功 **且** 超过保留期」—— 一台离线 35 天的机器若按录完时刻算，
会在**刚归档那一瞬间**就被删掉，那等于绕开了「至少一份副本」（I2）的意图。
§9 的验收判据原文就是「离线 35 天后才归档的段，**归档当天不算已过期**」。
现在用回执里的 `TimeAnchor`。

`Plan` / `PlanPerBusinessType` 因此多一个**必填**参数 `archiveAnchors`
（`evidenceId → 归档成功时刻`），表里没有某个 id 就是「还没归档」。
必填是刻意的：默认值会让「忘了传归档状态」变成一种合法输入，
而它正好会删掉唯一副本。手机端 `lifecycle.dart` 的 `planCleanup` 也是必填，
两端同一个理由、同一套口径（三条豁免的顺序也按 §3.5.3 自己的编号）。

⚠️ **谁来提供那份归档时刻表，目前还没有答案。** 回执里就有
（`ReceiptPayload.TimeAnchor`），但 `ReceiptStore` 只有按 id 查一个的 `FindAsync`，
没有「一次读全表」。要接上的第一步是给它加 `LoadAllAsync` ——
**现在故意不加**：在本类有生产调用点之前，那会是一段没人调用、也没法验证的代码
（正是本仓 §28 那种「写完了、测过了、没插电」）。

### 已知：一个间歇性失败的测试

`DesktopServicesTests.端到端_启动时收尾上次没走完的会话` 约 **1/7 概率**失败，
连跑 6 次全过、单跑必过。根因大概率是 `FreePort()` 的「关了再还」写法：
它 `Stop()` 掉探测用的监听再返回端口号，而别的测试可能在这中间抢到同一个端口。
**这是既有问题，与本次清理功能无关**，但没修 —— 修它要改成「一直持有到绑定时刻」，
那会牵动 PlaybackServer 的装配方式。先记在这里。

# 装配与接线（2026-09-23）

## 28. 装配的最后一跳

一次盘点查出**三处「写完了、测过了、没插电」**，全都落在组合根上：
功能代码在 Core 里、各自的测试全绿，而把零件接起来的那几步在 App 层、
或者根本没有被任何人调用。它们有一个共同点：**失效的表现全都是「没反应」**。

### 28.1 回放服务与孤儿收尾从没启动过

`DesktopServices.Create` 与 `DesktopServices.StartAsync` 是**两个**方法，
而 `AppHost.StartAsync` 只调了前者。三个功能因此静默失效：

- 收尾上次没走完的孤儿（规格 §3.1.1）—— 那段录像既不进索引也播不了；
- 回放服务（M3 的验收项）—— 网页回放**从来没有起来过**；
- 主窗口的「局域网回放页」按钮 —— 它读 `Server.BaseUrl`，那个值只在 `StartAsync`
  里才有 ⇒ **永久禁用**。

而 `README.md` 与窗口上的文案都按「会起」来写（「启动即用：应用会先收尾上次
没走完的录像，再起回放服务」）。这正是 `IMPLEMENTATION.md` §384 说的
「看起来完成了」。

### 28.2 编排循环从没被启动（最严重的一处）

`RecordingSession.RunAsync` 里那个循环负责**滚段**（§3.1.1）、**时长兜底**（§3.3.4）
与**磁盘将满主动收尾**。它在 `src` 里**一个调用点都没有** —— 协调器只调
`StartAsync` 起了第一个分段就结束了。后果不是「档位不生效」那么小：

- 整场只录一个**永不滚动**的分段。段不滚 ⇒ manifest 里一段都没封闭
  ⇒ 进程被杀后**什么都恢复不出来** —— 而滚段存在的理由正是这个。
- 时长兜底永不触发；磁盘将满也不会主动收尾。
- 「分段时长」「时长兜底」两个档位改起来毫无反应，根子在这里。

会话层对此**测得很透**（`RecordingSessionTests` 里一批 `FakeClock` + `AdvancingDelay`
用例，滚段、时长兜底、磁盘将满、编排异常全都覆盖），坏的只是没人起这个循环 ——
所以它躲过了整套 340 条测试。

现在协调器起循环，并用一次 `Interlocked.CompareExchange` **认领**
「这次收尾是我主动发起的，还是循环自己停的」：循环自己收尾时必须把它接回来，
否则 `_current` 会一直指着那个已经收尾的会话 —— 界面停在「录制中」，
用户会一直等一个永远不会发生的停录，也就不会去点【结束】。

### 28.3 三个档位只写不读

`AppSettings.SegmentMinutes` / `DurationFallback` / `StaticStop` 有界面、有落盘、
有变更日志，**没有任何读者**。现在：

- 前两个经 `RecordingSessionOptions.From` 送到会话 —— 映射**只此一处**，
  写两遍早晚会不一致，而不一致的表现是「界面上写着 5 分钟、实际按 1 分钟录」，
  极难被发现。越界值**夹回合法区间**而不是抛：设置文件是可以被手改的，
  一个改坏了的配置不该让用户录不了像（I4 的同一条精神）。
- `WorkModePolicy` 的 `Mode` / `StaticStop` 从 readonly 字段改成**可写属性**，
  由协调器写穿。设置页那句「工作模式立即生效」从此是真的 ——
  在此之前它只在重启后成立。

「时长兜底 = 关闭」用 `TimeSpan.MaxValue` 表示「永远比不到」，而不是把它改成可空：
循环里只有一次比较，没有任何算术，所以不必为此加分支和一圈可空判断。

### 28.4 ⚠️ 这一批靠一条**文字绊线**挡回归，它的天花板要说清楚

`AppHost` 在 `VidLog.Desktop.App`（WPF、`net9.0-windows`），而测试工程是 `net9.0`，
**引用不了**；App 层也没有自己的测试工程。所以「组合根少调了一步」这类 bug
对整套测试**完全不可见** —— 28.1 就是这么漏过去的。

挡它的是 `DesktopServicesTests.AppHost_装配时会真的启动服务`：它读 `AppHost.cs`
的源码文本，断言那句调用还在。**这不是行为测试**，是这个项目已经用过的绊线手法
（另一条是许可独立性那条「今天是不会失败的」测试）。

天花板：它只挡「这一行被删了/被注释了」，挡不住「改成一个不跑的路径」。
**根治**有两条路，哪条都比绊线强：

1. 给 App 层一个 `net9.0-windows` 测试工程；
2. 把 `DesktopServices.Create` 与 `StartAsync` 合成一个**忘不掉**的方法
   （唯一入口 ⇒ 拿不到「未启动」的实例 ⇒ 这一步在类型上做不到忘记）。

那时这条绊线应当删掉。

⚠️ 还有一个坑值得记下来：绊线的第一版只断言「源码里有这串文本」，
而 `// await services.StartAsync(...)` 里**仍然含有**这串文本 ——
于是「把调用注释掉」这个最常见的失活方式反而抓不住。第二版改成逐行检查、
排除以 `//` 开头的行。

### 28.5 静止停录仍然做不了，而且原因不是「没时间」

它要的是**录制中拿到画面**，而那条路 §24 已经用实测否决过：多一路输出就多一条
会堵的管道，而堵住管道会一路顶到 ffmpeg —— 它连 `q` 都处理不了，只能强杀，
正在写的 MKV 尾部就丢了。另起一个取帧进程也不行：DirectShow 相机是**独占**的（§25）。

所以设置页那个下拉现在**如实写着它不生效**（踩坑 #13：一个改了没反应的开关，
用户只会以为它坏了），连「扫码静止停录」那个工作模式一起 —— 后者的静止判据
同样取不到输入。

要接上的候选路子是**取样正在写的那个 MKV 文件**：第二路只读文件、不碰相机，
绕开独占，也绕开管道拖垮录制。但它的可行性、以及对「写入中的 MKV」的读取行为
（索引还没写完），**必须真机 + 真 ffmpeg 验** —— 本机两样都没有。
所以这条**留作待办，不猜一个实现**：`FrameMotionDetector` 与
`MotionOptions` 的阈值本来就是「纸面推导、必须真机标定」（§26），
再叠一层没验过的取帧路径，等于把两件不确定的事焊在一起。

# 入网：二维码连接（规格 §3.4.5）

2026-09-24 决定：**6 位配对码由二维码取代**。二维码里只放两样东西 ——
电脑端的**可达地址**与**一次性短时效令牌**，**绝不含凭据**；
凭据只在 `claim` 那一步发放，且只发一次。

「必须站在主机屏幕前」这个前提**一个字都没放松**：码显示在电脑端屏幕上，
扫不到就进不来。令牌仍是**明文走在局域网里**的（与原来的 6 位码一样），
所以这一层挡的是「不在屏幕前的人」，**不挡**同在局域网里抓包的人 ——
不要误以为二维码更安全。

## 29. 电脑端界面那半（2026-09-26）

### 29.1 为什么单独开一个窗，而且是模态

塞不进主窗口：这张码要能被手机清楚地扫到，得占 280px 见方，旁边还不能堆控件
（主窗口密密麻麻）。

**模态**是为了「一次只有一张码」—— `DeviceRegistry` 只留得住**最后一张** session。
屏幕上摆着两张、能用的只有一张，那是最难解释的一种「扫了没反应」。

### 29.2 「同意 / 拒绝」的默认按钮必须是「否」

`MessageBox.Show(..., MessageBoxResult.No)`。默认落在「是」的话，回车、
或者随手关掉弹窗（许多人的肌肉记忆里，关掉 = 消掉这个提示）**都等于批准**，
而批准之后那台设备就能把录像传进来。这里宁可让人多按一下。

批准过 / 拒绝过的设备记在 `_asked` 里：同一条请求不再弹第二次。
**拒绝之后那条请求不清掉**（清了手机会看到「重新扫码」，而它只是等了一个「不」），
它下一轮轮询拿到的就是同一个答复。

### 29.3 发不出码时**绝不显示一张假的**

四种机器状态各自有话说：没装配回放服务 / 服务没起来 / 只绑到了本机（缺 urlacl）/
挑不到局域网地址。一律不画码，红字写清原因**和怎么才能好**。
少了后一句，用户看到的是一张扫不动的码 —— 而他会以为是手机的问题。

### 29.4 两处静默的坏法

- **心跳必须在轮询之前点**：`_ticker.Start()` 写在 `await PollAsync()` **后面**的话，
  `PollAsync` 里万一走到 `Expire()`（它停掉心跳），紧接着那一句又把它打开，
  从此**再没有人停它** —— 码已经失效了，倒计时却还在跳。
- **`_busy` 挡轮询重入**：WPF 的模态弹窗跑一个嵌套消息循环，
  `DispatcherTimer` 在里面**照样触发**，没有守卫的话一轮申请能弹出一串一模一样的窗。

设备列表每秒都被刷一遍，内容没变就不重设 `ItemsSource`（重设会重建整个列表，
用户正在看的那一行会跳一下）。

### 29.5 「深色是 0 还是 255」收口到 `EnrollQr.Pixels`

这个约定原先有**两份**：一份在测试脚手架的像素循环里，一份在界面层 ——
而**界面那份没人看**（测试抄得再对，屏幕上那份写反了照样是绿的）。

现在字节由 Core 的 `EnrollQr.Pixels` 摊，界面只负责放大
（`PixelFormats.Gray8` + `NearestNeighbor`），于是往返测试证明的是
「**画到屏幕上的那些字节**解得回原串」。用 `Gray8` 而不是 `BlackWhite`：
后者按位打包，"0 是黑还是白"得再看一次文档。

写反的表现是**一张反色码**：有静区、有方阵、比例也对，看着完全正常，**扫不出来**。
轴序写错则表现为**整体转置**，同样是合法图形，同样扫不出来。两种都只有拿手机去扫才知道。

### 29.6 ⚠️ 第二条件线，天花板与 §28.4 逐字相同

App 层没有测试工程 ⇒ 「界面上到底有没有地方能显示出那张码」对整套测试**不可见**，
而这件事**真的发生过**：2026-09-24 收工时 `PendingAsync` 与 `DevicesAsync` 是
**零调用点** —— Core 逻辑、单测、CI 全绿，屏幕上却没有地方显示二维码
⇒ 手机永远换不到凭据 ⇒ **M5 端到端走不通**。那不是「没联过」，是这一步根本没做。

挡它的是 `DesktopServicesTests.入网二维码在界面上真的有出路`：读四个文件的源码文本，
断言 `OpenSessionAsync(` / `PendingAsync(` / `DecideAsync(` / `new EnrollWindow(` 都还在。

天花板：只挡「有人把这一行删了 / 注释了」，挡不住「改成一个不跑的路径」。
根治同样是把 App 层做成可测的（见 §28.4 那两条路）；那时这条绊线应当删掉。

⚠️ 写这条时踩到的坑值得记下来：第一版的剥注释只删掉 `TrimStart()` 以 `//`
**开头**的行，于是**行尾内联注释**里的片段仍然留在文本里 ——
把调用改成 `var decided = true; // await ...DecideAsync(...)`，测试**照常绿**。
必须真正把片段删掉才红得起来。

### 29.7 手机端那半**还没做**（两端现在对不上）

`lib/upload/uploader.dart` 的 `enrollClaim({deviceId, code})` 仍然要一个**手输的 6 位码**，
而电脑端已经在发二维码 + 令牌。做手机端那半时要把它换成令牌，
并顺手删掉手机端 `README.md` 里说明这件事的那一段。

本机也没有摄像头，`AppHost` 在没有 ffmpeg 时直接抛。

# 已知缺陷（2026-09-26 盘出来的，**未修**）

## 30. 同一个采集进程可以被停两次 —— `_currentProcess` 的认领还是「先读后清」

### 30.1 现象

2026-09-26 跑预检时，`RecordingCoordinatorTests.连续扫下扫到异码就换段_旧段入库新段开录`
失败了一次：

```
System.IO.IOException : The process cannot access the file
'…\work\20260926T040625-a0bf5a2e\segment-000.mkv' because it is being used by another process.
  at …File.WriteAllText(String path, …)
  at …RecordingCoordinatorTests.FakeProcess.StopAsync(…)        ← 假采集进程往分段里写字
  at …RecordingSession.DisposeAsync()                 (RecordingSession.cs:522)
  at …RecordingCoordinator.DisposeAsync()             (RecordingCoordinator.cs:487)
```

**这是偶发，不是回归**：同一份代码全套跑了 **11 次**（4 次带 ffmpeg：363 通过 / 2 跳过；
7 次不带：351 通过 / 14 跳过），**只有上面那 1 次红，其余 10 次全绿**；
单独跑那条用例也过。
`segment-000.mkv` 被两个写入者同时打开 —— `File.WriteAllText` 之间会拿
`ERROR_SHARING_VIOLATION`。

### 30.2 读出来的机制（不是猜的）

1. `RecordingSession.DisposeAsync`（[RecordingSession.cs:510](src/VidLog.Desktop.Core/Recording/RecordingSession.cs#L510)）
   先 `CancelAsync()` 掉编排循环，**但没有等那个循环 Task 收完**，就去停 `_currentProcess`。
   `CancelAsync()` 只等取消回调，**不等**在 `await _delay(...)` 上被取消的异步续体跑完。
2. 循环的 `finally` 走 `TryStopAsync` → `StopAsync` → `CloseCurrentSegmentAsync`
   → `ReleaseCaptureAsync` → **也停同一个进程对象**。
3. `ReleaseCaptureAsync`（[RecordingSession.cs:425](src/VidLog.Desktop.Core/Recording/RecordingSession.cs#L425)）
   对进程的认领是「先读、后清」：

   ```csharp
   var process = _currentProcess;
   if (process is null) { return; }
   var exitCode = await process.StopAsync(…);   // ← 两边都读到非 null，两边都停
   _currentProcess = null;
   ```

   于是同一个采集进程被**停两次**，两个写入者并发落同一个分段文件。

⚠️ 这个「先读后清」的写法，项目**已经点过名**：`CloseCurrentSegmentAsync`
（[RecordingSession.cs:451](src/VidLog.Desktop.Core/Recording/RecordingSession.cs#L451)）
的注释里写着「先读后清会让两边都通过判据」，并为此改成了 `Interlocked.Exchange` ——
但那次只覆盖了**分段**（`_openSegment`），**没有覆盖进程**（`_currentProcess`）。

### 30.3 后果有多重

- **真 ffmpeg 上后果轻**：`FfmpegCaptureProcess.StopAsync` 把 stdin 写失败的三类异常
  （`IOException` / `InvalidOperationException` / `ObjectDisposedException`）都吞了。
  所以表现至多是「多写了一个 `q`」，或者一次被吞掉的异常。
- ⚠️ **但这条没验过**：`StreamWriter` 不是线程安全的，两个线程同时写有可能抛出来的
  **不是**那三类里的任何一个 —— 那就会变成一条用户可见的
  「录制过程中出错」（[RecordingSession.cs:295](src/VidLog.Desktop.Core/Recording/RecordingSession.cs#L295)）。
- **假进程没有这层防御**，所以这条 flake 现在**是在替真进程挡这个洞**：
  不该拿它开刀（例如给 `FakeProcess` 加锁或加 try）—— 那等于把唯一的信号掐掉。

### 30.4 ✅ 2026-09-27 修了（触发条件变了）

当时不修的理由是「要先能稳定复现，而它是 11 次全套里 1 次」。**今天它变成例行挡住 CI**
（连推两次都撞上），于是按上面那条候选改法做掉：

- `ReleaseCaptureAsync` 改 `Interlocked.Exchange(ref _currentProcess, null)` 认领，谁认领谁停；
- `DisposeAsync` **不再自己读一遍** `_currentProcess`，改调 `ReleaseCaptureAsync` ——
  两个入口共用同一个认领（那正是原来看漏的地方：只改一个入口等于没改）。

**实测**：修前 6 次里 2 次红（就是这一族）；修后 **12 次里 1 次红，而那次是另一条 flake**。

⚠️ **它没有把 flake 清零**：§27 的 `FreePort()` 与
`PlaybackServerTests.每个请求都留下一条带_trace_与状态码的日志`（2026-09-26 加的）
仍然偶发红 —— **那是另外两条，别把这次的修复当成"套件干净了"。**

# 生产级日志（2026-09-26）

需求方原话是一次性给的一整套（结构化 / 全局异常带堆栈 / 请求任务出入 / 脱敏 /
集中收集 / 轮转）。**照着那份清单逐条比对之后，有四件事与它的前提不符**，
四件事都决定了做法：

1. **没有 `print` 可替代**：`Console.WriteLine` / `Debug.WriteLine` / `Trace.WriteLine`
   在这个仓里**全仓 0 处**。要补的是**能力**，不是替换调用点。
2. **已经有自建设施，而且形状是对的**：`IAppLogger` + `FileLogger`（有界 Channel、
   丢日志不丢录制）+ `LogRetention`（按**文件名里的时间戳**排）+ `DiagnosticsPackage`
   （zip 导出，刻意排除视频与 PII）。
3. **本仓自己否决过引库**（见 §32.1 引的那句原文）。这次**不推翻它**。
4. **模板里的 DB / Redis / MQ / Docker / K8s 一个都不存在**：这是裸机 Windows 应用，
   「请求中间件」的落点是进程内那个 `HttpListener`。

## 31. 日志行：JSON Lines、级别阈值、按批刷盘

### 31.1 为什么是 JSON

诊断要能**按字段查**（「这台机器昨天有没有 5xx」「哪几次收尾失败」），
而 grep 一段自由文本做不到。一行一个对象：

```json
{"ts":"2026-09-26T17:10:05.123+08:00","lvl":"INFO","cat":"录制","msg":"开录 SF123","trace":"a3f19b02","data":{"会话":"abc"}}
```

`ts` 用**带偏移量**的 `"O"`：原来那个格式没有偏移量，同一个诊断包里两台机器的
`17:10` 是歧义的，而排事件顺序正是要拿它。

`data` 的值**只认标量，其余写 `<对象:Xxx>` 占位**（`FileLogger.WriteValue`）。
⚠️ 刻意**不反射**：反射式序列化会把 `EnrolledDevice` 的凭据原样写进日志，
而诊断包会把 `logs/*` 整个打包外发。**少一条诊断信息，好过凭据出差。**

### 31.2 两个撞出来的坑（都不是设计出来的，是跑出来的）

- **默认编码器不能用**：`JavaScriptEncoder.Default` 把非 ASCII 全部转义 ——
  一句中文消息变成一串 `u` 加十六进制，时间戳里的 `+08:00` 也一样。
  那仍然是**合法 JSON**，但**这份文件既没法读也没法 grep**（`grep 开录` 一条都搜不到），
  而它是要人打开来看的诊断文件。改用 `UnsafeRelaxedJsonEscaping`
  （「Unsafe」= 不转义 HTML 敏感字符，而这份文件不会被塞进 HTML/JS 执行）。
- **常开句柄会把外部读取者挡在外面**：`File.ReadAllLines`（以及记事本、支持脚本）
  会拿到「文件正被另一个进程使用」，而改动前是每行开一次关一次、读得到它。
  **一份打不开的日志等于没有日志** ⇒ 退回**按批开关**：一个突发里的 N 行
  合并成一次 open/write/flush/close，比改动前只会更好。
  顺带没有了「句柄指着已删除文件」那个坏法。

### 31.3 级别与刷盘

`FileLogOptions.MinLevel`。默认 `Debug`（= 改动前的行为，测试与临时排查要它），
`AppHost` 正式运行时按**构建配置**传（`#if DEBUG` → Debug，否则 Info）——
生产上开着 DEBUG，日志会被淹掉，而**淹掉的日志等于没有日志**。

`FlushAsync()` 靠**一道屏障**（队列里的项是「一行日志 或 一个屏障」，
后台循环把屏障前面那些行写完才放行它）。没有它，`FlushAsync` 只能靠 sleep 猜。

## 32. 脱敏：三层，而且**在写盘之前**

诊断包会把 `logs/*` 整个打包外发，而 `devices.jsonl` 不进包**只是靠约定** ——
哪天有人手滑加一句目录遍历，盘上的明文凭据就跟着出去了。
**写入即干净只需要一个过滤器；导出时再过滤就是第二个。**

| 层 | 做什么 | 硬度 |
|---|---|---|
| **结构层** | `data` 只收标量，其余写类型名占位 | 最硬：序列化器**根本不认识**对象图 |
| **键名层** | `SensitiveName.Is`（与配置变更留痕**同一份判据**）⇒ 值换成「（已修改）」 | 中 |
| **值层** | 登记过的密钥值抹成 `***` + `Authorization: Bearer …` 那条正则 | 最软 |

⚠️ **天花板（诚实说清楚）**：值层只挡得住**登记过的**那一个。没登记过的、
被变换过的（重新 base64、转大写）、第三方库异常消息里内嵌的 —— **一律挡不住**。
正则解决不了「有人把不该记的东西记了」；这里做的是把爆炸半径压小，不是消灭它。
所以**新生成密钥的那段代码有义务顺手登记一次** ——
`DeviceRegistry.NewToken()` / `NewCredential()` 就是这么做的，
`LoadAllAsync` 读回来的那批也登记（覆盖这次改动之前就发出去的那些）。

那条 `data 里塞一个对象 → 落盘行里读不到它的属性` 是**绊线**，不是普通单测。

## 33. 全局异常：崩溃那一行**同步写**

这个应用是 `WinExe`（**没有控制台**），而在此之前
`AppDomain.UnhandledException` / `DispatcherUnhandledException` /
`TaskScheduler.UnobservedTaskException` **一个钩子都没有** ⇒
未捕获异常的表现是**窗口直接消失、磁盘上一个字都没有**。

`Platform/CrashGuard.cs` 挂在 **App 工程**（要 WPF 的 `DispatcherUnhandledException`，
Core 引不了 WPF）。三个钩子各挡一类，第三类尤其要紧：
.NET Core 默认把「没人 await 的 Task 异常」**静默丢掉**，
而本仓有好几处 `_ = Task.Run(...)`。

⚠️ **崩溃那一行用 `FileLogger.WriteSync` 同步写，不走队列**：进程随时会被终止，
`DisposeAsync` 那两秒的等待**根本等不到** —— 于是最要紧的那条遗言恰好落不下。
它同时**不受 `MinLevel` 限制**（阈值是给日常噪声用的，不是给遗言的）。

顺序也改了：原来是「先建 AppHost」（logger 在它里面才建），所以**启动过程中崩掉没有记录**，
而启动失败恰恰最需要现场。现在：先建日志器 → 装钩子 → 再启动。

⚠️ **UI 线程那个钩子不设 `e.Handled = true`**：UI 线程上炸过一次之后控件树可能已经是坏的，
继续跑比退出更危险。这一刀改的是「留下记录」，不是「让它活下去」。

## 34. 请求出入与 `trace`

`PlaybackServer.HandleAsync` 是**全站唯一的单一入口/出口**，而它此前一行日志都没有、
出错那个 `catch` 还是**静默吞掉**的（只回 500）⇒ 「手机传不上来」在电脑端**完全无迹可查**。

出口记一行，`method` / `path` / `status` / `耗时ms` 都是**独立的字段**
（不是塞在消息里）；`status >= 400` 记 Warn。
⚠️ 只记出口、不另记入口：出口那行已经有方法、路径、状态与耗时，
入口行提供不了新信息，只会把量翻一倍。

`trace` 由 `Trace.Start()`（`AsyncLocal<string>`）在入口设，
**`FileLogger` 自己从异步上下文里取** —— 调用点一个字都不用传。
为什么必须这样：一次上传要过七八层、中间 `await` 到别的线程上，
**每层多传一个参数的话，漏传一层就是那一段日志串不起来**，
而串起来正是它存在的全部理由。两条性质各有用例钉住
（`await` 换线程后不变；两个并发任务互不串 —— 后者正是不能用 `[ThreadStatic]` 的原因）。

## 35. 边界留痕：只铺边界类，用可选参数

**`IAppLogger? logger = null` → `NullLogger.Instance`**：测试里那 35 处构造调用
**一行都没改**。不引静态 service locator —— 它只买到「够得着 static 方法」，
而可选参数也够得着，代价却是一个可变全局。

**只铺边界，不铺十五个类**：`SystemProcessRunner` 一处就覆盖
`RemuxPipeline` / `DecodeVerifier` / `EncoderProbe` 五个类。
其余落点：`SessionFinalizer`（I9 的唯一落点）、`DeviceRegistry`（安全事件，
**绝不记凭据**）、`UploadReceiver.commit`、三处自起进程。

⚠️ **外部进程只在失败时记**（记的是 ffmpeg 自己说的 stderr 尾巴）：
那三条链路每次收尾都要跑，成功也记的话日志会被正常流量淹掉。

### 35.1 ⚠️ 一条试出来的教训：「这些类会记」≠「有人递给它们」

先写完 `BoundaryLoggingTests`（直接构造那三个类、传自己的 logger），
然后**故意把 `DesktopServices` 里的 logger 参数摘掉** —— **全绿**。
因为那些用例证明的只是「这些类会记」，**不是「生产上有人把 logger 递给它们」**。
与 §28「装配的最后一跳」一模一样的洞，这个项目已经栽过三次。
补了装配绊线 `组合根把日志器递给了三处边界` 之后，再摘掉那一处就红了。

## 36. 保留期：补上「那一跳」

`LogRetention.SelectExpired` 写对了、有 4 条测试盯着它，而在 `src` 里**零调用点** ——
于是 `AppSettings.LogRetainDays` 一路传进 `FileLogOptions` 之后成了死值：
**日志只增不减**，而整套测试全绿。与 §28 同一类毛病。

新增 `FileLogger.PurgeExpired`（列目录 → 交给 `SelectExpired` 挑 → 逐个删，
删不动就跳过那一个），装配点 `AppHost.StartAsync`，并把删了几个**记一条日志** ——
一次没有任何日志的清理，出事时说不清它到底跑没跑。

⚠️ `RetainDays < 1` 时**整个不删**：那种配置下「过期」会把今天这个正在写的文件
也算进去，而删掉正在写的日志是纯损失。

⚠️ **顺手订正一处调研结论**：`MainWindow` 保存设置用的是 `AppSettings with { … }`，
`with` 会把**没列出的属性原样带走** —— 所以 `LogRetainDays` 不是「每次保存被重置」，
而是「界面上没有地方能改它，只能手改 `settings.json`」。留痕那边已经盯着它。

## 37. 错误扫描（规格 §6.1）—— 两端都补上了

`docs/01-行为规格书.md` §6.1「必须保存的事实」点名要有
「错误扫描 | 错码保护触发的事件（诊断用）」，而在此之前**两端都没实现**：
错码保护只做了提示与播报，事后查不出操作员那一刻扫到了什么。

形状照母仓 `docs/02-数据模型.md` §1.7 那张表，四个字段逐字对齐，
**两端同一个文件名、同一层位置、同一套键名**（`<root>/scan-errors.jsonl`）。

⚠️ **写失败不能把这一下带下去**：本表按规格「不是控制流的输入」，
而这一下正在**录着像**。诊断记录丢了是小事，让错码保护这条路径整个失败是大事。

⚠️ **与手机端一处有意的不对称**：手机端的诊断包里**带**错误扫描记录
（并标明「包含单号」）；电脑端的不带 —— 它那条「刻意排除 PII」的规矩本来就不收单号。
理由不是偷懒：**扫错码的是手持设备那边**，电脑端的记录来自本机扫码枪，
真出事时要看的是手机上那份。

# 工作模式与闲置提醒（2026-09-27）

## 39. 删掉「扫码静止停录」，换成「闲置提醒」

规格 §3.3.1（2026-09-24）：「**电脑端不要静止停录，电脑端只保留连续扫码和同码停录模式。**」
§3.3.3 给电脑端换了一条判据：连续 N 分钟**没有任何扫码或打点** → 语音播报提醒，
**由用户自己决定要不要结束录制**；原话「**它只提醒，绝不改录制状态**」。

### 39.1 这一刀基本上是「删」，而且删得干净

删之前查过生产调用点：`WorkModePolicy.OnStatic` **一个都没有**（只有测试调它）——
与 §28.5 记的一致（电脑端拿不到画面）。所以删掉的是：
`WorkMode.StopOnStaticAfterRescan`、`OnStatic`、`WorkModeState.StaticFor`、
`TrackedWaybillLeftFrame`、`RescanStaticHold`、界面下拉项，以及那 5 条测试。

⚠️ **不是"改成永远通过"，是那几个行为在这端不存在了。** 手机端仍然是三种模式。

### 39.2 ★ 一个试出来的事实：**电脑端存的是数字，不是名字**

规格 §3.3.1 的老配置兼容写着「设置文件里存的是**模式名字**……读到 `scanThenStaticStop`
时回落到「同码停」」。**核实后：那句话对手机端成立**（Dart 存 `name`），**对电脑端不成立** ——
本仓没挂 `JsonStringEnumConverter`，枚举一律按数字存
（`SettingsStoreTests` 里写的就是 `{"ArchiveBackend":1,...}` 这种字面量）。

所以老配置的实际形态是数字 `2`；删掉那个成员之后它是个**越界值**，落在各个 switch 的
兜底分支上**恰好看着像同码停**。靠巧合是对的，但**不是要求** ⇒ 现在显式 `Normalize`：
越界的模式 → **同码停** + 一条用户可见的警告（选同码停的理由与规格那句一致：
它**会自己停**，不会一路录到把盘写满）。

### 39.3 闲置计时：「从开录那一刻起算」是**结构性成立**的

规格 §3.3.3 要求「闲置计时**从开录那一刻起算**，不能拿『上次扫码到现在』当起点，
否则架机半小时后一开录就会立刻被提醒」。

落点是**「开一段本身也算一次活动」**：而开一段只可能由一次扫码触发
（`SubmitAsync` 与其中的换件），所以开录那一刻必然刚更新过 `_lastActivityAt`。

⚠️ **我先写的是「再按本段已录时长封顶」，试了才知道那是无效守卫**：它永远不生效
（idle 不可能超过段龄），却会让功能在假时钟的测试里**永远不触发**。删掉了，
把不变式写进 `_lastActivityAt` 的注释里 —— **谁新加一条「不经过扫码就开段」的路径，
那就是这条不变式破的时候。**

### 39.4 ★ 一个把既有 flake 放大的坑（这一批最值得记的）

看门狗的第一版是「无论档位是开是关都起」，于是**每个协调器一个每秒醒一次的定时器**。
测试里 `Build()` 造了几十个协调器、全都用「关闭」档 ⇒ 几十个定时器白跑，
而并行跑的全套里这种白跑**把既有时序敏感用例的窗口撑大了**：

| | 全套连跑 |
|---|---|
| 看门狗常开 | 6 次里 **2 次红**（`连续扫下扫到异码就换段` 等 §30 那一族） |
| 档位关闭时**根本不起**看门狗 | **8 次全绿** |

「关闭」的语义本来就该是连看门狗都不跑。**这条 fix 不只是省资源 ——
它让套件重新稳下来。** 变红配方也因此特殊：它不是「某条用例变红」，
而是「**既有的 flake 频率上升**」。

### 39.5 语音：`System.Speech`（本仓第二个 NuGet 依赖）

规格要的是「**语音播报**提醒」，而电脑端此前**没有任何发声设施**（全仓搜
`Speech`/`SpVoice`/`Beep` 零命中）。出口做成**托盘气泡 + 语音**两条：
窗口多半收在托盘里，只弹气泡的话用户根本看不见。

⚠️ `System.Speech` 是微软自带的包，**只调 Windows 的 SAPI，不携带任何音频数据** ——
「不许引入音频素材文件」那条账没被破坏（与手机端走系统 TTS 同一条理由）。
⚠️ 一切失败都吞掉：没装语音包、引擎被禁用都不该影响录制（I4 的同一条精神）。

### 39.6 验证状态

桌面端 **432 通过 / 2 跳过**。新增：`WorkModePolicyTests` 的闲置那组 8 条
（含「**闲置提醒绝不产出停录**」—— 遍历所有档位断言不出现 `StopSegment`）、
`RecordingCoordinatorTests` 3 条、`SettingsStoreTests` 2 条。

变红配方两条：① 去掉 `Normalize` 的回落 ⇒ 只有「老配置回落到同码停」那条红；
② 把看门狗改回常开 ⇒ 全套 6 次里 1~2 次红（**既有 flake 频率上升**，不是某条用例红）。

⚠️ **只有真机能验的**：提醒真的响（气泡 + 语音）、而且**不打断录制** ——
`TrayIcon.Notify` 与 SAPI 在本机没有窗口、也没有语音引擎可验。

## 40. 归档层四档 + 真正的「第二份」（规格 §3.4.6）

第 3 刀的前半。规格（2026-09-24 需求变更）：「NAS 和百度网盘同时做，加一项，
用户可挂载网络驱动器存储盘。」四种后端：**电脑端本地 / NAS / 百度网盘 / 挂载网络驱动器**。

### 40.1 ★ 开工前发现的一件事：**这个设置以前什么都不做**

规格 §3.4.6 要求四档「对上层表现一致」，而实现前只有两个枚举值
（`LocalDisk` / `Nas` / `Cloud`），**没有任何一个后端实现** —— 全仓只有
`LocalFolderArchiveBackend`（只认本机磁盘）。更糟的是：

- 界面能选 NAS / 网盘（`ArchiveCombo`），能存进 `settings.json`；
- 但**没有任何一行代码读它去决定「东西放哪儿」**。`ArchiveRoot` 是写死的
  `<root>\archive`（`DataLayout`），上传接收、收尾发布、回放、清理全都直接吃它。

所以那时选了 NAS 的用户，得到的是「**改了没反应的开关**」（踩坑 #13）——
而这正是这一刀要修的东西。

### 40.2 模型的澄清：**本机一份 + 归档层一份**，而不是「换个地方存」

规格 §3.5.1 的判据说得很清楚：「归档层 ≠ 电脑端本地时才允许开清理」，
理由是**那时本地这份才不是唯一副本**。反过来说：

> 只有「本地那份 + 别处的第二份」这个模型下，
> 「按保留期清掉本机那份」才是安全的、也才是 §3.5.2.1 那些设置的意思。

所以这一刀**没有**把 `ArchiveRoot` 改成「用户配置的那个 NAS 目录」——
那样一来选了 NAS 之后本机就没有副本了，保留期设置会变成**清空气**。
改成的是：

```
本机副本   <root>\archive          ← 索引里的相对路径相对它解析（不变）
归档层      ArchiveTarget 说的那个地方 ← 第二份，发布过去
           LocalDisk 时两者是同一个地方（所以不给清理）
```

⚠️ **这与计划里那句「`ArchiveRoot` 全改成按配置解析出的根」不一致** ——
那是看到代码之前的设想；按代码与规格对上之后，正确的做法是给
「第二份」造一条通路，而不是把本机那份搬走。记在这里备查。

### 40.3 发布点只有两处，而它们都要接

| 来源 | 发布点 |
|---|---|
| 电脑端自己录的 | `SessionFinalizer` 写索引之后 |
| 手机端传上来的 | `UploadReceiver` 提交之后（回执与索引都已落盘） |

`ArchiveRelay` 把「发布 + 失败留痕」收成一处 —— 写两遍必然走岔。
⚠️ 归档层就是本机时**根本不建 relay**：那时发布是空操作，
建它只会让「发过没有」这个问题多一个没意义的答案。

### 40.4 ★ 方向性判据：**发布失败绝不动本机那一份**

- 不删本机副本、不回滚索引、不改回执；
- 代价是「**这条还不能被清理**」—— 回查会拒（I8），那正是安全的方向；
- 失败要**看得见**：日志一条 Warn + 设置页一行橙字
  （「盘上这一份现在只有一份，发上去之前别删它」）。

写反了（发布失败 ⇒ 收尾失败）会把本机这份变成孤儿、每次启动重收一遍 ——
**拿 I2 去换一个「发上去了没有」的仪式**。变红配方见 §40.7。

### 40.5 路径绝不进索引（规格 §6.2）

`Z:\` 与 `\\nas\vidlog` 只当**配置里的根**。`RelativePath` 本来就拒绝绝对路径与 UNC，
所以索引里存的仍是 `<单号>/<会话>/<段>` 这种相对路径 ——
换一台机器把它挂到别的盘符，索引照样读得出来。

### 40.6 发布到一半断了怎么办：`.part` 后缀

先写 `<名字>.mp4.part` 再改名。半截文件如果叫 `.mp4`，回查会把它当成
「那一份在」，而它根本播不了。`.part` 不在回查的判据里，所以下一轮会重发。
（同名已存在时**不覆盖**：归档路径由「单号 + 会话 + 序号 + 时间」推出来，
同名就是同一条录像，覆盖等于抹掉归档层上可能更早、更可信的那一份。）

### 40.7 变红配方（实测过）

把 `SessionFinalizer` 里那段 `if (_relay is not null) await _relay.PublishAsync(…)`
改成 `&& false` ⇒ **只有**这两条红：

- `收尾之后归档层上也要有一份`
- `归档层发不上去时本机这一份照样入库`（它同时证明「失败不改本机那份」这条方向）

### 40.8 验证状态

桌面端 **469 通过 / 2 跳过**（本批 453 → 469）。新增：
`ArchiveBackendTests`（14：档位、目录型发布/覆盖/.part、回查分得清「不存在」与「查不了」、
relay 失败留痕）、`SessionFinalizerTests` 2 条、`SettingsStoreTests` 2 条。

⚠️ **测试里的「NAS」就是一个本地临时目录** —— 这不是偷懒，而是规格自己定的口径
（「网络那一层由用户自己在系统里解决，我们只当成一个目录用」）。所以**能验的是**
发布/覆盖/半截/回查这条链，**验不了的是**「那个目录真的在网络那头」——
真机（真 NAS / 真映射盘）走一遍才算数。

⚠️ **百度网盘那一档还没实现**（`ArchiveBackendKind.Cloud` 有枚举、有界面项、
有「要授权」的配置提示，但没有后端）。它要真接口 + 真账号，本地一行都验不了 ——
按本项目对「写完但没插电」的一贯态度，**宁可晚写**。它的位置留给下一批：
接口已经按「两档」设计好（目录型 / 网盘型），补一个 `IArchiveBackend` 实现即可。

## 41. 保留期：两个数 → 四个数（规格 §3.5.2.1）

第 3 刀的后半之一。规格 2026-09-24 的原话：「本机可以选择存储的退货和发货视频保留多久，
**已备份保留多久，未备份保留多久**，退货和发货视频分开选择。」选项 9 项
（不保留 / 3 / 5 / 7 / 10 / 15 / 30 / 自定义 / 全部保留），默认「全部保留」。

### 41.1 ★ 两列语义相反 —— 这一节最要紧的一句话

| 列 | 到期做什么 | 起算点 |
|---|---|---|
| **已备份** | **真删本地副本**（先过 §3.5.4 回查） | **归档成功时刻**（回执的 `timeAnchor`） |
| **未备份** | **只标红、只催上传，永不自动删** | **录完时刻** |

未备份那一列是**唯一副本**（§3.5.3① 的硬豁免，I2），删了就永久没了。
所以它在代码里的落点是一个**新的输出列表**（`CleanupPlan.OverdueUnarchived`），
而不是候选列表里的东西 —— **它连一个候选都产生不出来**，这是结构性的，
不靠「记得别删」。

⚠️ 它与豁免列表（`Exempted`）也**不是一回事**，所以没并进去：
豁免回答的是「它为什么**没被删**」（几乎每条录像都在豁免里），
而催上传要回答的是「**它该被催**」—— 界面上要据此标红、计入「N 个未备份」。
两者混在一起的话，界面上分不出「正常保留」和「该催了」。

### 41.2 模型换掉了，老设置文件要认得出来

原来那个 `RetentionPolicies`（发货 / 退货各一个 `RetentionPolicy`）**删掉了** ——
它就是规格替换掉的那个「两个数」。`RetentionPolicy` / `RetentionMode` 留着：
它们是 `Plan` 这个原语吃的「一份天数策略」（外加「按空间」那一档，它是全局的）。

老 `settings.json` 里那个键下是 `{"Outbound":{"Mode":1,"KeepDays":7},"Return":{…}}`。
**不认它的话那两个数会被静默丢掉**（反序列化跳过未知属性），
用户看到的是「我明明设过 7 天，怎么变回全部保留了」。所以：

- `RetentionSettingJsonConverter`：一个档位读写成一个整数（`null` = 全部保留），
  **同时认老的对象形状**（`Mode` 0/1/2 + `KeepDays`）；
- `RetentionSettings.LegacyOutbound` / `LegacyReturn`：老键名，只读；
  读到了就搬进**已备份那一列**（语义没变，只是多了一列），并说一句。

⚠️ **「按空间」那一档在新模型里没有对应值**，老文件里遇到它回落「全部保留」
（朝少删的那头落）。它若真要做，那是**另一条触发路径**（磁盘满没满与业务类型无关），
不是保留期档位 —— 见 §3.5.2 那张老表格。

### 41.3 ★ 三个 System.Text.Json 的坑（都是测试抓到的，一次也没白踩）

1. **位置记录 + 参数化构造 ⇒ 缺失的属性被填 `default`**，而槽位是引用类型
   ⇒ 四个槽位全成了 `null`，下一个碰它们的 `PlausibleDays` 当场 NRE。
   改成「无参构造 + 属性初始化器（`= KeepAll`）」就对了：**「缺」应该是「全部保留」**。
2. **`HandleNull` 默认 false ⇒ `null` 绕过转换器。** 写出去的是 `null`
   （「全部保留」没有天数可写），读回来却没人接 —— 同样是那一串 NRE。
   开了 `HandleNull => true` 之后，`Write` 里又必须容忍 `value` 本身是 null。
3. **同一个转换器不能同时表示两种「null 语义」。** 老格式那两个键的 `null`
   意思是「**老文件里没有它**」，而四个槽位的 `null` 意思是「全部保留」。
   混用之后**每一次存读都被误判成「从旧格式迁移」**，还平白多一条警告。
   所以老格式那两个键走一个**单独的** `LegacyRetentionSettingJsonConverter`
   （它不覆盖 `HandleNull`，null 保持 null），并且写盘时用
   `WhenWritingNull` 把它们挡掉。

### 41.4 ★ 越界的天数**不在转换器里宽容**

`RetentionSetting.FromConfig` 是宽容的（认不出 → 全部保留），**但转换器刻意不用它**：
宽容会让一个手改出来的 `-5` 被**静默**改成「全部保留」——方向对（朝少删），
可用户不会知道自己的设置被改过（I3）。转换器把越界值和认不出的类型
都原样留着（后者给一个 `-1` 哨兵），交给 `AppSettings.IsPlausible` 去拦：
判否 ⇒ **整份回落默认值 + 一条警告**。

**宽容留给另一头**：界面上手输的文本。那里「随便给什么都行」是对的。

### 41.5 上限 3650 天是**实现标定**的

规格 §3.5.2.1 明说这类阈值「不写死在这里……由实现标定并记进 `docs/实现决策.md`」。
本仓标定 **10 年（3650 天）**：远大于任何真实工位的保留期，
而小于「手抖多打几个 9」那种值（`99999` 会被拦下并整份回落）。

### 41.6 界面：一张两行两列的表

行 = 已备份 / 未备份，列 = 发货 / 退货（规格点名的摆法）。
⚠️ 第 9 项「自定义」**不是一个列表项，是一个手输的数** ——
所以这四个下拉是 `IsEditable="True"` 的，用户直接敲「45」就行，
不必为它造一个输入弹窗（WPF 里没有现成的 `InputBox`）。
下面四行说明里明写了「未备份那一列**永不自动删**」——
不说清楚的话，用户要么以为坏了，要么以为自己选了「马上删」而不敢选。

### 41.7 变红配方（实测过）

在 `PlanPerBusinessType` 的未备份分支里塞一句 `candidates.Add(…)` ⇒
**只有**这两条红：`未备份那一列到期只催上传_绝不产生候选`、
`已备份的那些不受未备份那一列影响`。

### 41.8 验证状态

桌面端 **478 通过 / 2 跳过**（含本批新增 14 条：未备份列 5 条、四个数独立 3 条、
档位与回落 2 条、设置往返与老格式迁移 4 条）。`precheck.ps1` 全绿。

## 42. 清理链路**第一次插电** + 归档层回查接口

第 3 刀的最后一块（电脑端这半）。此前 `CleanupPlanner` / `CleanupExecutor` /
`CleanupAuditLog` **整套都是零生产调用点** —— 写好了、测过了、从没接上过
（母仓 `HANDOFF.md` §6 第 19 条记的就是这种病）。

### 42.1 预告与执行**分成两个方法**

规格 §3.5.5 原话：「**禁止静默清理**」「清理前必须给出预告
（将删除多少条、多少容量）」。所以 `CleanupService` 是：

| 方法 | 做什么 |
|---|---|
| `PreviewAsync` | 读索引 + 标签 + **回执的时间锚**，算出计划。**一个文件都不碰。** |
| `RunAsync` | 逐条回查归档层 → 删 → 写审计 |

合成一个方法的话，「先给用户看」这一步就靠调用方记得 ——
而在这类**不可逆**动作上，那种「靠记得」的约定不该存在。

⚠️ **时间锚来自回执**（`ReceiptStore.LoadAnchorMapAsync`，本次新加）。
`CleanupPlanner` 的注释里早就写了「要真接上，第一步是给 `ReceiptStore` 加一个
一次读全表的方法」—— 那个「故意不加」的理由（没有生产调用点）现在不成立了。

### 42.2 触发点：**启动时算一次，用户点了才删**

没有别的触发点（规格没有定义「什么时候该清一次」）。启动时那一次排在
**孤儿收尾之后** —— 顺序反了会让人以为「刚收回来的那段被清了」。

界面上是 `MessageBox`：条数 + 容量 + 三条安全说明（回查、删的是本机那份、
锁与 24 小时的豁免），**默认按钮是「否」** —— 不可逆的动作不该让回车键替用户点头。
没有候选时**不打扰**：每次开机弹一句「没什么要清的」是噪音，
而噪音会把真正该看的那一次淹掉。

### 42.3 ★ 两道闸，判据是同一个

「归档层是本机磁盘 ⇒ 不许清理」（规格 §3.5.1）落在**两处**：

1. `CleanupService.CanCleanup` → 界面上**连问都不问**；
2. `CleanupExecutor.CanCleanup` → 就算被绕过了，也逐条拒绝并写审计。

只有第 1 道的话，一个「手工造出来的计划」就能删掉唯一副本；
只有第 2 道的话，用户会看到一个摆在那儿、点了没反应的入口（踩坑 #13）。
测试里两条都有 —— `归档层是本机时_哪怕计划里有候选_执行层也一条都不删`
那一条就是**绕过界面直接调执行层**。

### 42.4 归档层回查接口（手机端「手动删除」的前置闸）

`POST /api/v1/archive/verify`（形状写进母仓 `docs/05-上传接口形状.md`）。

- 要凭据（与 `/api/v1/upload/*` 同一套 Bearer）；
- 请求体就一个 `location`（索引里那个**相对路径**）；
- 回 `{exists, couldNotVerify, reason}` —— ⚠️ **「查不了」必须与「不存在」分开报**：
  对用户是两句话，而两者都导致不删；把「查不了」当成「不存在」，
  删掉的可能就是最后一份（I2）。
- ⚠️ **路径校验就是这条接口的安全边界**：它是**远端**调的，所以
  `RelativePath.Parse` 会拒掉绝对路径、UNC 与 `..` 越级 ——
  放过去的话，手机端就能问「`C:\Windows\notepad.exe` 在不在」。

### 42.5 变红配方（实测过）

把 `CleanupService.PreviewAsync` 里的时间锚换成一张**空表** ⇒ 4 条红
（`起算点取自回执的时间锚`、`归档层上真有一份时才删`、`执行时逐条回查`、
`目录型归档层允许清理`）—— 因为「没有锚 ⇒ 一条都够不着候选」，
这正是「起算点取自回执」那条链的作用。

### 42.6 验证状态

桌面端 **489 通过 / 2 跳过**（478 → 489）。

| 新增 | 条数 | 管什么 |
|---|---|---|
| `CleanupServiceTests`（新） | 7 | 两道闸、**预告不碰文件**、起算点取自回执、回查不通过不删且留审计、删了要留审计 |
| `PlaybackServerTests` | +4 | 回查接口：还在 / 不在且与「查不了」分得开 / 没凭据 401 / **路径越级一律拒** |

⚠️ **顺带记一条观察**：这一批给 `PlaybackServerTests` 又加了 4 个起真
`HttpListener` 的用例，而那个 fixture 用 `FreePort()` 抢端口（§27 记过的 flake 源）。

## 43. 未校准不得录制（规格 §3.6.3 / §3.6.4）

规格 2026-09-24 的需求变更，也是 I10 被**主动收窄**的那一条：
原文是绝对的「无网可用」，现在改成「**已校准之后**的无网可用」。
需求方明知后果并接受：「一个只有内网、工位电脑从没联过公网的打包间，这套系统开不了工。」

### 43.1 时间线 = 锚 + 单调读数，与墙钟无关

`TrustedClock.Now` = `AnchorUtc + (当前单调读数 − 拿到锚时的单调读数)`。
规格 §3.6.3 原话：「**水印与时长都不得取自墙钟** —— 用户改系统时间**不得**
改变视频里的时间」。所以 `RecordingSession` 的起录时刻改读它（不接可信时钟的
那几十条测试路径仍读墙钟，行为与从前一致）。

⚠️ 锚**落盘**（`<root>/calibration.json`）：规格 §3.6.4「已校准状态**落盘持久化**，
之后离线照常录制」—— 不落盘的话，一台交付后从没联过网的机器重启一次就再也录不了。

### 43.2 ★ 一道闸不够，要三道

| 闸 | 挡的是 |
|---|---|
| `RecordingCoordinator.StartWork()` | 点了【开始工作】—— 并且**当场把原因说出来**（不然用户只看到「点了没反应」） |
| `RecordingCoordinator.StartSegmentAsync()` | **「没按开始就扫码」那条路**（扫码枪是硬件，不等用户点按钮） |
| `RecordingSession.StartAsync()` | 一切直接建会话的路径 |

⚠️ **第二道是写完第一道之后才发现的**：`StartSegmentAsync` 里有一段
「扫码枪打进来时用户未必先点过【开始工作】」的逻辑，它会**自动把工作置为进行中**。
只有第一道的话，绕开闸门只需要「直接扫一张面单」—— 而规格对手机端明确写了
「`startWorking()` **以及扫码开录那条路**」两道都要有，两端同一个道理。
**变红配方**：把第二道改成 `if (false && …)` ⇒ 只有 `未校准时不开始工作_而且当场说出来` 红
（它同时验「没开录」与「有没有话」）。

### 43.3 ★ 跳变检测：能测什么、测不了什么（诚实边界）

规格 §3.6.3 要求「每次启动都要核对一次挂钟与上次退出时留下的记录是否自洽」，
验收判据是「**改完时间再重启，仍然不该录得进去**」。

| 情形 | 判得出来吗 |
|---|---|
| **同一次开机内**，墙钟前后跳 | ✅ 双向都测得出（单调钟连续，两者一比就知道） |
| **跨重启**，时间**被调回去** | ✅ 墙钟比上次记录的还早 —— 这正是 I11 点名的伪造方向 |
| **跨重启**，时间**往后调**／正常关机过了一夜 | ❌ **分辨不出来**，只能放行 |

⚠️ 第三行是**有意的取舍**：`Stopwatch` 的单调读数**跨重启归零**，所以重启之后
没有任何本地信号能证明「中间过了多久」。那时要求重新校准的话，一台每晚关机的
机器天天早上都录不了 —— 而规格 §3.6.4 承诺的是「已校准之后离线照常录制」。
所以那里**放行**，并如实记在这里（**不假装它测得到**）。

⚠️ 容差 **120 秒**是**本仓标定**的（规格明说这类阈值「由实现标定并记进该仓的
`docs/实现决策.md`」）：NTP 校正是毫秒到秒级、时区变更与用户改时间是小时级，
两分钟足以分开两者，又不会因为一次正常的系统对时而误判。

### 43.4 电脑端的锚**只能来自公网**

规格 §3.6.4 的两个来源里，「归档回执里的时间锚」对电脑端**不适用** ——
回执上的 `TimeAnchor` 正是**它自己**盖的（`UploadReceiver` 用 `_now()`）。
手机端才有两个来源。所以电脑端这一半只有 HTTP Date 一条路，
而这正是规格那句「电脑端必须自己有过一次公网校准：它正是归档回执里那个锚的来源」。

⚠️ **用 HTTP Date 而不是 NTP**：NTP 走 UDP 123，在没有管理权限的机器上常被防火墙拦；
HTTP 走 80/443，与这台机器上网用的是同一条路。规格允许两者取一。
⚠️ 它的精度是**秒级**，而且信任中间那段网络 —— 对这份用途够用：
要挡的是「用户手动改系统时间」，不是国家级对手。规格 §3.6.3 也明令
**不得宣传「不可篡改的时间」**。

### 43.5 界面说清三件事

设置页新增【时间校准】一块：**为什么**（视频里的时间要能追溯到本机之外）、
**怎么办**（点【重新校准】；只有内网、从没联过公网的机器开不了工，这是接受过的代价）、
以及**未校准只挡住新录**（已有录像照常检索、回放、导出、交付）。

拿不到公网时间时**不猜一个时刻**：猜出来的锚比没有锚更糟 —— 它看起来是校准过的。

### 43.6 验证状态

桌面端 **502 通过 / 2 跳过**（489 → 502）。新增 `TrustedClockTests` 11 条
（未校准的拒绝、落盘、时间线、HTTP Date 解析、双向跳变、跨重启放行、
坏文件当作未校准、取不到时不猜）+ `RecordingCoordinatorTests` 2 条（两道闸）。

⚠️ **只有真机能验的**：真断网 / 飞行模式下的行为、以及**真的去改系统时间再重启**
（那是这一条的验收动作本身）。本机只能验状态机。

## 44. 水印烧进视频（规格 §3.6.2）

规格 2026-09-24 的需求变更：「自动在视频打水印，**年/月/日/时/分/秒**……在开始工作
扫描到快递单号时，对视频添加**完整快递单号**水印。」追问后补充：时间是**按秒走的**、
参照**北京时间**；位置**避开取景框、在最上方中间**。

### 44.1 ★ 为什么不用 `drawtext`：它的时间只有墙钟

| 能用什么 | 问题 |
|---|---|
| `%{localtime}` / `%{gmtime}` | **墙钟**（规格明令：水印的时间不得取自墙钟，§3.6.3） |
| `%{pts}` | 帧时间戳，**没有日期类型** —— filtergraph 表达式做不了日期运算 |
| `%{pts:gmtime:…}` | 把 pts 加到**进程启动那一刻**上；但那个基准是**本机时区**的墙钟，没法固定成 UTC+8 |

ASS 则是**我们算好每一个字**：每秒一条字幕、文字由
`WatermarkText.ClockLine` 从**可信时钟**推出来 —— 时区、格式、按秒走三件事
都在我们手里，而且**纯数据、可测**。

⚠️ **必须在采集那一次就烧**：收尾是 `-c copy` 的 remux，那一步**加不了滤镜**
（加了就要重编码，违反「不转码」）。所以是「录的时候就在画面里」，不是「导出时再叠」。

### 44.2 ★ 本机真的验到了「画进画面」（不是只验了字幕文件写对）

`WatermarkTests.端到端_水印真的画进了画面` 用本机 ffmpeg 渲同一帧两次
（一次带 `ass=`、一次不带），比 PNG 大小：**30 KB vs 6 KB**。

判据不是「看起来对不对」（本机看不见图），而是「**有/没有水印差得出来**」——
它挡不住「字画歪了」，挡得住「**根本没画**」。后者才是真正会静默发生的那种
（字幕写了、字体找不到、滤镜没接上 —— 三者都表现为**屏幕上一个字都没有**，
而不会有任何报错）。顺带确认了本机 libass + `Microsoft YaHei` 能用。

### 44.3 一处踩到的转义：Windows 路径里的冒号

`-vf ass=C:\work\x.ass` **直接解析失败**（filtergraph 把 `:` 当选项分隔符），
表现是 ffmpeg 起来就报错、**录不了像**。
`AssWatermark.EscapeFilterPath` 把它写成 `ass='C\:/work/x.ass'`（单引号包起来、
反斜杠换成正斜杠、冒号转义）—— **一处产出**，有测试钉着。

### 44.4 其它几个刻意的选择

- **字体走系统**（`Microsoft YaHei`）：不随包带任何字体文件（规格 §10 的许可证账目）。
  找不到时 libass 自己退到默认字体 —— 字可能不好看，但**内容仍然对**。
- **黑描边**：白字压在**白面单**上时没有描边就完全看不见 ——
  与界面上那四角括号同一个理由（§3.2.2）。
- **单号里 `{}` 与 `\` 要转义**：ASS 用它们做覆写标记，扎到的话轻则这一行消失、
  重则把后面的字幕一起吃掉。
- **字幕用完就删**：它是这一段的临时素材，不是产物。留在会话目录里会跟着进归档。
- **写失败不让采集失败**：那一段没有水印是遗憾，**录不出来是事故**（I2 的同一条精神）。
- **覆盖时长 = 段时长 + 2 分钟**：段会按时长滚动，但最后一段可能超出一点。
  少了余量就会出现「最后几秒没有水印」—— 而**部分缺失比全都没有更难发现**。

### 44.5 变红配方（实测过）

把「每秒一条」那个循环改成 `for (var i = 0; i < 1; i++)` ⇒ **只有**这两条红：
`每秒一条_而且时间跟着走`、`没有单号时不写那一行`。

### 44.6 验证状态

桌面端 **515 通过 / 2 跳过**（502 → 515）。新增 `WatermarkTests` 13 条
（北京时间与设备时区无关、补零、不截断、每秒一条、红/白样式、两行不重叠、
字号随分辨率、特殊字符转义、ASS 时间格式（含总小时数那条）、argv 位置与转义、

### 45.1 ★ ④ 是**显示名**，不是磁盘文件名

规格那句「`快递单号.mp4`」说的是**列表里显示的名字**。磁盘文件名与归档路径

### 45.2 缩略图：本机 ffmpeg + **落盘缓存**

规格原话：**不得每次进页面都重新抽帧**。抽一帧要解一段视频，一页十几条就是几秒 ——
而它每次翻页、每次刷新都会重来一遍。所以：`<root>/thumbnails/<evidenceId>.jpg`，
判据是**文件在不在**（不是「我们抽过没有」——后者在重启之后全部落空）。

⚠️ 新增 `GET /api/thumbnail/{evidenceId}` 端点：**它只端出已经抽好的那张**，
不现抽。抽帧发生在别处（页面第一次拿到搜索结果时按需补），因为浏览器渲染列表时
会挨个发请求 —— 在那里跑 ffmpeg 就是十几秒的卡顿。

⚠️ 没有缩略图时回 **404**，页面**把那格清空**（而不是留着浏览器的破图图标）：
破图图标看起来像「这一段坏了」，而其实只是还没生成。

抽帧命令的产物是 `<名字>.jpg.tmp` —— 而 **ffmpeg 靠扩展名猜输出格式**，
`.tmp` 它猜不出来，于是**永远失败**，表现只是「一张缩略图都没有」（不报错、不崩）。

（假 runner 会照样绿 —— 它只验「产物写出来了没有」）。

## 46. ★ 那条 flake 有了根治：起 `HttpListener` 的测试串行跑

§42.6 / §45.5 记的那条「偶发一次、重跑就绿」，2026-09-27 一天里出现了**三次**
（电脑端两次、手机端一次）。三次都重跑就绿 —— 而**「重跑就绿」正是最坏的那种信号**：
它让人开始无视红，而下一次真红会被当成又一次 flake。

### 46.1 机制（不是猜的）

那一族测试用同样的办法挑端口：**先绑 0 号端口拿到一个空闲端口 → 关掉 → 用它开服务**。
两个测试**并行**跑时，两边可能挑到**同一个**端口 —— 后起的那个绑不上就红了，
而**代码一行没错**（母仓 `HANDOFF.md` §27 记的就是这条）。

### 46.2 处置：把竞态从根上拿掉，而不是把 flake 藏起来

新增 `HttpListenerCollection`：起真 `HttpListener` 的两个测试类
（`PlaybackServerTests` / `DesktopServicesTests`）**同一个 xUnit 集合**，于是**串行**跑。
同一个时刻只有一个监听器 ⇒ 端口冲突从根上没有了。

**实测**：改完连跑 **4 次全绿**（改之前一天里三次偶发红）。

⚠️ 代价是这一族不再并行 —— 它们本来就要起真服务、真发请求，是最慢的几个，
串行之后全套慢了一两秒。**值得**（见上面那句「重跑就绿是最坏的信号」）。

⚠️ **根治它的是串行，不是「多试几次」**：如果哪天有人为了快把它们拆回并行，
这条 flake 会原样回来。

## 47. 许可只限机位（规格 §3.9 / `04-许可设计.md`）

第 8 刀。**机位 = 允许接入的手机端台数**；占用公式 `手机台数 + max(0, 摄像头数 − 1)`
（今天恒等于手机台数 —— 第一路相机是白送的，它同时喂预览、识码与录制）。

无服务端：用户在本机看到**机器码** → 给卖家 → 卖家签发 → 同一个界面粘回来。
**ECDSA P-256 验签**，机器码取 WMI 三项（主板序列号 / CPU ID / BIOS 版本）。

### 47.1 ★ 固定测试向量当场顶出一个真 bug：载荷布局差一字节

签发工具与客户端在**两个仓**（L1：私钥与它绝不进客户端的仓），
所以格式必然有两份实现 —— 那就必须有一个「两边对不对得上」的物证。
本次钉的是 `LicenseTests.签发工具产出的码_客户端验得过`：**签发工具真的产出过的一个码**
（公钥、机器标识、码三样写死在测试里），客户端这边必须验得过。

**它第一次跑就红了**，而红的方式很有意思：

```
Expected: 77        ← 签的时候给的序号
Actual:   4127195213   ← 0xF600004D
```

签名验过了、机位数对了、机器码也匹配了，**只有序号是垃圾**。原因是载荷布局：

| 字段 | 偏移 | 长度 |
|---|---|---|
| `issuedDay` | 3 | 3 |
| `serial` | **6** | **4**（6/7/8/9） |
| `mc[3]` | **10** | 15 |

而实现里写的是 `mc` 从**第 9** 字节起 —— 与 `serial` 的最后一字节重叠，
短哈希的首字节把序号的高字节盖掉了。**读写是同一处错，所以自洽地绿着**：
码验得过、机器码也匹配，`ToBytes`/`FromBytes` 往返一致，此前所有用例全绿。
它唯一的表现就是这个「序号变成垃圾」，而序号只用于售后追溯，没人看。

> **这一条值得记下来的理由**：同仓的往返测试**永远**发现不了这一类错
> （读写同一处错 ⇒ 往返恒等）。两个仓各写一份、错法不一样，才顶得出来 ——
> 那正是「格式有两份实现」这件事唯一的价值，也是它唯一的安全网。

修完之后补了一条 `载荷的字节布局逐字节钉住`：把 25 个字节**逐字节**断言一遍
（含「第 9 字节必须是 0」那一句），让同一个错法不必再靠另一个仓才发现。
母仓 `04-许可设计.md` §3.1 那张表也加了偏移列。

### 47.2 ★ 一处写完又删掉的防线：机位闸门只留一道

机位闸门最自然的写法是**两道**：`RequestAsync`（报到）一处、`ClaimAsync`（签发凭据）一处。
第二道写完才发现它**永远走不到**：

一张码只服务一次入网（领走凭据时 `_session` 被置空），所以「批准与领取之间被插队」
这个口子根本不存在 —— 同一张码下第二台设备去领的时候拿到的是
「没有待批准的请求」，压根到不了签发那一步。

而且**查不到的防线写不出会红的测试**。按本仓的规矩（每条防线都要有一条能证明
它拦得住东西的用例），删掉了第二道，把理由写进 `SeatBlockedAsync` 的文档注释，
并留了一条 `一张码只服务一次入网_所以超限的设备走不到签发那一步` 当**提醒**：
将来真要让一张码服务多台设备，那条会红，那时必须把闸门搬进 `ClaimAsync`。

### 47.3 已在网的设备一律放行 —— 这不是漏洞，是必须的

闸门只挡**新的**手机接进来（L5：超限只拒绝新手机接入，已在线的继续录、不打断）。
所以「这台设备已经在登记簿里」时**必须放行**：它占的是**已有的**那个机位，
重扫一次码只是换一份凭据。

不放行的话，「机位满了之后手机丢了要重配」会变成死局 ——
而用户手里那个激活码明明是够的。有专门一条用例钉住这半边。

### 47.4 许可没配好时，机位数取 0

`VIDLOG_LICENSE_PUBKEY` 没配（部署漏了）时 `license` 是 `null`，机位数取 **0**
⇒ 一台手机都接不进来。这是刻意的：这个档位的全部意义就是「允许接几台手机」，
没有激活就没有机位。而「软件没配好」这件事由启动警告**说给用户**，
激活失败那句话也明说「这是安装的问题，不是你激活码的问题」——
不说准的话，用户会一直去找卖家换码，而换了也没用。

### 47.5 界面：机器码**一直**显示

设置页新增【许可（机位）】：机器码（只读 + 一个【复制】）+ 激活码输入框 + 一行状态。
⚠️ 机器码**不激活也显示**：它是用户唯一需要抄给提供方的东西，而那件事发生在
**他还没激活的时候**。藏在「激活之后」的界面里等于没有。

⚠️ **降级（某段 WMI 读不到）必须显示出来**：全零段的机器码没有任何区分度，
同型号的机器会互相匹配 —— 用户拿它去签发，签出来的码在别人的机器上也能用。

【复制】包一层 try：剪贴板是跨进程共享资源，别的程序占着它时 `SetText` 会抛
`COMException`。为这个崩掉界面不值得，但也不能装作复制成功了 —— 失败时明说
「请手动选中复制」。⚠️ 顺带踩到一次编译错：**本仓同时引了 WinForms**（托盘图标），
`Clipboard` 在 WPF 与 WinForms 里撞名，必须写全 `System.Windows.Clipboard`。

⚠️ 激活之后**不用重启**：`LicenseBlockedReason` 读的是 `_license.Status`（活值），
所以当场就能开工。反过来（运行中失效）才要重启，那是 L7 的「运行期定冻结」。

### 47.6 签发工具：**独立仓**，私钥在仓外

`D:\VidLog-Signing`（新仓，`vidlog-sign`）：`keygen` / `pubkey` / `issue` 三个动作。
它**不引用客户端任何代码** —— 格式是照着规格重写的一份（与 47.1 那条向量配对）。

⚠️ `KeyFiles.Create` 会**拒绝往任何 git 仓里写私钥**（往上找 `.git`）。
私钥一旦提交过，就算下一个提交删掉它，它也已经在那台机器的 `.git` 里、
在任何一次 `git clone` 过的机器上了 —— **那件事没法回头**。
`.gitignore` 里那三条是第二道。
⚠️ **本次没有生成任何生产密钥**：验证用的是临时目录里的一把，用完即删。
生产密钥要由持有者自己 `keygen` 出来并妥善备份（丢了就签不出新码）。

## 48. ⚠️ 容量系数：两端码率机制不同，这张表对手机端偏小约 2 倍（**已记录，未改**）

查「第 2 刀的连带项」（容量预告必须按当前录制规格估）时核出来的一件事。
**它不是新引入的 bug，是一个一直存在、今天不爆、将来会咬人的偏差。**

### 48.1 事实：两端录出来的东西**码率机制根本不同**

| | 怎么定码率 | 真实码率 |
|---|---|---|
| **电脑端** | `FfmpegCameraCapture.BuildArguments` 里**一个码率参数都没有** ⇒ 编码器默认的 **CRF** | 随画面走，**没有上界** |
| **手机端** | **显式设码率**（8 Mbps @720P 按像素等比放大、H.265 打六折）—— Android `KEY_BIT_RATE` / iOS `AVVideoAverageBitRateKey`，**硬目标** | 就是那个目标值附近 |

而 `BytesPerSecond` / `bytesPerSecondOf` 那张表**两端共用**（这是计划点名的要求，也对）。
问题是：**表是照电脑端标定的。**

### 48.2 差多少

| 档 | 手机端目标码率 | 表里的值 | 比值 |
|---|---|---|---|
| 720P H.264 | 8 Mbps | 550 KB/s（4.4 Mbps） | 0.56 |
| 1080P H.264 | 18 Mbps | 1100 KB/s（8.8 Mbps） | 0.50 |
| 4K H.264 | 72 Mbps | 4000 KB/s（32 Mbps） | 0.46 |
| 720P / 1080P / 4K H.265 | — | — | 0.47~0.60 |

**每一格都偏小 1.8~2.25 倍。**

### 48.3 ★ 偏小是**危险的那一头**

`Plan` 的「按空间清理」是 `freed += size` **攒到够为止**：

- size **偏大** ⇒ 几条就够 ⇒ **删得少** ✅ 安全
- size **偏小** ⇒ 以为每条更小 ⇒ **要删更多条才凑够** ⛔ 删的是**不可逆的证据**

这条表自己写着「偏大估」，而对手机端它**不成立** —— 也就是**实现违背了自己声明的口径**。

### 48.4 ⚠️ 今天先**不改数值**，理由是两者都没实测

- 手机端那个 18 Mbps 是**算出来的**（`bitRate` 的公式），不是从真录的文件量出来的；
- 电脑端 CRF 下的真实码率**从没实测过**（本机没有摄像头，那两条集成测试是跳过的）。

⚠️ 拿一组纸面推导换掉另一组纸面推导，只是把「已知偏小」变成「未知」。
本仓对这类事的一贯态度是**宁可晚做，不猜着做**（§40.8 百度网盘那条同一个理由）。

**今天的影响面是有限的**：「按空间清理」在界面上**没有入口**
（保留期四个数只有「不保留 / N 天 / 全部保留」），所以 `EstimateBytes` 目前
只喂给**预告数字** —— 偏小的表现是「说要腾出 50 MB、实际腾出 100 MB」，
方向无害。

### 48.5 钉住它的是一条**绊线**（手机端）

`recording_spec_test.dart` 的 `★ 表比我们自己的目标码率小约两倍 —— 这是已知偏差，不是没注意`：
遍历六个档位断言 `表 < 目标` 且 `比值 > 0.4`。

**它不是在验正确**，是在把「已知偏差」变成**看得见的**：改 `bitRate` 公式会红、
改容量表也会红。红的时候**两件事必须一起看**。

**变红配方（实测过）**：把 `bytesPerSecondOf` 的 `(h264, uhd4K)` 从 4000 改成 9000
（= 把表调成跟手机端一致）⇒ **两条红**：
`★ 表比我们自己的目标码率小约两倍`（比值 1.02，不再小于 1）
+ `两端同一张表`（桌面端还是 4000，这条同时证明跨端那半边也钉着）。

⚠️ 顺带记一个**我自己踩的单位坑**：`bitRate` 是 **bit/s**，而 `bytesPerSecondOf`
返的是**字节/s**（它内部那个表才是 KB/s）。第一版断言写成 `bitRate / 8 / 1024`，
算出「表比目标大 1000 倍」那种胡话 —— 注释里已经把这一处标成本类断言最容易看错的地方。

### 48.6 什么时候**必须**解决（容量系数）


**接上「按空间清理」那一档之前。** 那一步要求拿两端**真录的文件**实测标定
（文件大小 ÷ 时长），然后把表和那条绊线一起换掉。

⚠️ 在那之前，**别为了让预告数字好看去动这张表** —— 它现在唯一的用途是预告，
而它将来要决定删多少条。

## 50. ★ 时长兜底：到点**先问**，不是直接停（规格 §3.3.4）—— 一条做反了的规格

拿规格逐条对照代码时查出来的，**性质是回归**：电脑端把这条做成了「到点直接收尾」，
而 2026-09-21 那次需求变更的**唯一动机**就是「它会把正常录制打断」
（规格 §3.3.4 的 📌 框里写着「原设计下只要录过 4 分钟就一定被问一次，
而连续扫这类模式本来就可能有较长的正常录制 —— 它会把正常录制打断」）。

也就是说：**那次变更是为了修掉这个行为，而电脑端恰好就是那个行为。**

### 50.1 规格要的是什么

```
录制中 ──4 分钟──> 语音：「录制时间即将超时，是否需要停止录制？」
                  ＋ 屏幕出现两个按钮【停止】【继续】
      点【停止】   点【继续】    1 分钟无操作
       立即停止   取消本轮上限    默认继续
                 进入下一轮      ──> 到 5 分钟自动停止
```

三条硬要求：**交互是「语音提示 + 屏幕按钮」（不用扫码）**、
**「无操作」与「主动继续」必须区分**、**提示与按钮必须在「录制不被中断」的前提下出现**。

### 50.2 电脑端原来是什么

`RecordingSession.RunAsync` 的循环里：

```csharp
if (Elapsed >= _options.MaxDuration) { reason = StopReason.DurationFallback; break; }
```

没有询问、没有按钮、没有等待窗口。默认档（4 分钟）下**任何一段正常录制到 4 分钟就被切断**。
讽刺的是 `WorkMode.cs:69` 的注释写着「命中后要**询问**用户是否继续，不是直接停」——
注释与实现正好相反。

**手机端是做对的**（`stop_controller.dart` 的 `_evaluateTimers` + `RecordPromptAnswered`），
所以这是**两端行为不一致**。

### 50.3 新口径：与手机端**逐条同形**

| | 手机端 | 电脑端（本次） |
|---|---|---|
| 首问时机 | `effectivePromptAfter` = 档位值 | `MaxDuration`（语义从「到点停」改成「到点问」） |
| 再问间隔 | `durationPromptRepeatEvery` = **5 分钟** | `PromptRepeat` 默认**同一个 5 分钟** |
| 宽限期 | `durationPromptGrace` = **1 分钟** | `Grace` 默认**同一个 1 分钟** |
| 关档位 | `_nextPromptAtMs = null` ⇒ 不问不停 | `_nextPromptAt = null` ⇒ 不问不停 |

⚠️ 三个常量**逐字同值**（5 / 1）—— 两端对这条的表现不一致时，用户会以为其中一个坏了。

⚠️ 一个刻意的实现差异：手机端把询问做成**事件链上的一个事件**
（`DurationPromptAnswered`），电脑端做成**会话的回调 + 协调器转发**
（`RecordingSession` 构造参数 `durationPrompted`）。
理由是电脑端**不能**为此新起一个定时器 —— 这个仓已经因为「档位关闭时还在白跑的定时器」
把既有的 flake 放大过一次（§39.4），而测试里会造几十个协调器。
回调是会话在**它自己的编排循环里**发现该问了才触发，零额外定时器。

⚠️ 会话**没有**为此多一个依赖：它只持有一个 `Action?`，不知道通知那一层的存在。

### 50.4 ★★ 变红证明里发现的**第二个**问题（比第一个更值得记）

按规矩，做完要证明「把旧行为塞回去，新测试会红」。塞回去之后：

```
失败 时长兜底答继续_不停_隔一轮再问
失败 时长兜底到点先问_答停止之后才收尾并把状态接回来
```

**而最该红的那条 —— `时长兜底到点是先问_录制不中断` —— 没红。**

它当时的核心断言是 `Assert.False(loop.IsCompleted)`（「循环还没结束 = 还在录」）。
为什么测不住：到点直接停的话，循环 `break` 之后**还要跑收尾**
（remux / 解码校验 / 写索引，全是真文件 IO），而断言执行的那一刻收尾**很可能还没做完**
—— 于是 `loop.IsCompleted` 仍然是 `false`，**断言照样绿**。

> 又是「测试绿在一个巧合上」，而且是**我自己刚写的那条测试**。
> 它绿在「收尾比断言慢」这个时序巧合上，与 §21 记的「圈数奇偶」是同一族。

改成**确定性判据**：等**假时钟再被推进 5 分钟**。
循环真在跑的话时钟必然继续走；停了的活没人推进它，`WaitUntilAsync` 必然抛。
—— 再塞回旧行为，**三条全红** ✅

⚠️ 顺带记一条**测试脚手架的坑**：`WaitUntilAsync` 第一版用 `Task.Delay(5)` 让出执行权，
而假时钟下循环一圈只需一次 `await` ⇒ 那 5 毫秒里循环跑了**几千圈**，
「询问之后、宽限到期之前」那个窗口**根本插不进去**（表现为「等不到第二次询问」）。
改用 `Task.Yield()` 只让出一次执行权，窗口才是可控的；上限也从「墙钟毫秒」改成「圈数」。

⚠️ 还有一条：假 `AdvancingDelay` 原来**忽略取消令牌**（真的 `Task.Delay` 会抛），
于是「取消之后循环退出」这条路在测试里**永远走不到** ——
用 `cts` 收尾的用例会 `await` 到天荒地老（实测挂到 600 秒超时）。补上了
`ThrowIfCancellationRequested`。**这三处都是本次修这条时才暴露的测试缺陷，
不是实现缺陷。**

### 50.5 界面接线（App 层没有测试工程，所以只能靠绊线）

- ⚠️ 停段 / 换件 / 结束工作时**收起询问条** —— 那两个按钮答的是一次已经作废的询问。

## 51. ★★ 三条「重跑就绿」的根因（其中一条是**生产 bug**）

修 §50 时全套跑红了一次（`每个请求都留下一条带_trace_与状态码的日志`），
按老规矩「重跑就绿」不能放过 —— 连跑 6 次抓到现场，**顺着它又挖出两条**。

⚠️ **§46 那句「别把这次的修复当成套件干净了」在这里再次应验**：
§46 根治的只是**抢端口**那一族，这**三条是另外的**（读日志的共享模式 / 关服务的竞态 /
临时目录清理）。

### 51.1 ★ 关回放服务时会抛异常（**生产代码的竞态**，不只是测试问题）

现场：

```
InvalidOperationException : Please call the Start() method before calling this method.
  at System.Net.HttpListener.BeginGetContext(...)
  at PlaybackServerTests.WaitForLogEntriesAsync  ← 其实是 StopAsync 那条路
```

机制：`StopAsync` 先 `CancelAsync()`、再 `_listener.Stop()`，而挂在
`GetContextAsync` 上的那一句在**这两者之间**可能以 `InvalidOperationException`
结束（listener 已经不在监听了），**而不是**以取消结束。原来的 catch 列表是

```csharp
catch (Exception ex) when (ex is OperationCanceledException or HttpListenerException or ObjectDisposedException)
```

—— `InvalidOperationException` **不在里面** ⇒ 异常逃出循环 ⇒ `_loopTask` 变成
faulted ⇒ `StopAsync` 里 `await _loopTask` 把它**抛给调用方**。

**后果**：用户关回放服务（或程序退出）时可能报错。而它在测试里的表现是
「某条不相干的用例偶尔红」，所以一直没被当成生产问题。

修法：把 `InvalidOperationException` 加进那个 catch。
⚠️ 这不是「把异常吞掉」：那个 `try` 块里**只有 `GetContextAsync` 一句**，
所以在这个位置能抛的 IOE 只有一种含义 —— **listener 已经不在监听了，循环该退出**。
注释里写清了这一点（否则下一个人会以为是乱吞）。

### 51.2 ★ 读日志用了太严的共享模式

现场：`IOException : The process cannot access the file '...log' because it is being used by another process.`

机制：写者（`FileLogger`）**做对了** —— 它用
`FileShare.Read | FileShare.Delete`（允许别人读，也允许删）。
而**读方**（测试里的 `WaitForLogEntriesAsync`）图省事用了 `File.ReadAllLinesAsync`
—— 它的默认共享模式是 **`FileShare.Read`，意思是「我读的时候不许别人写」** ——
两边一撞就是 IOException。

⚠️ **诊断包导出读日志用的是同一个口径**（`FileShare.ReadWrite`）—— 照它抄就对了，
**别另立一套**。修法是把读方改成 `FileShare.ReadWrite | FileShare.Delete` 并容忍 IOE。

⚠️ 这类红的**原因与它要验的事毫无关系**，正是「重跑就绿」最坏的那种（§46 那句话）。

### 51.3 ★★ 22 份重复的 `TempDir`，一处漏了 catch 就散成「随机测试红」

现场（第三次抓到的那条，报在一条**完全不相干**的用例上）：

```
UnauthorizedAccessException : Access to the path 'segment-000.ass' is denied.
  at System.IO.FileSystem.RemoveDirectoryRecursive
  at ...TempDir.Dispose()
```

机制：测试结束时**会话的收尾可能还没做完**（水印 `.ass`、分段 `.mkv` 还被持有），
而 Windows 在「文件被另一个进程持有」时**可能报 `UnauthorizedAccessException`
而不是 `IOException`** —— 而 22 个测试文件里各自定义的那份 `TempDir`
**全部只 catch `IOException`**（`ArchiveBackendTests` 那份更彻底：**一个 catch 都没有**）。

**后果**：任何一条测试在清理临时目录时都可能被这个异常打红，而**报红的名字是那条测试**
—— 看起来像「那条测试有问题」，其实是清理阶段的事。这就是它一直以
「随机某条测试偶尔红」的形态出现的原因。

修法：22 处统一放宽成
`catch (Exception ex) when (ex is IOException or UnauthorizedAccessException)`，
理由写在每一处（4 行注释，`ArchiveBackendTests` 那处补上缺失的 try）。

⚠️ **这 22 份重复本身就是病因**：同一件事写 22 遍，改一处修不到另外 21 处。
本该抽成一个共享的 `TempDir`（那才是「一处产出」）。本次**没有**做那个重构 ——
先止血，把「22 份重复该合并」记在这里，等下次动测试脚手架时一起做。

| | 全套连跑 |
|---|---|
| 修**前** | 6 次里 1 次红、8 次里 1 次、10 次里 1 次（三条轮着来） |
| 修**后** | **12 次全绿** |

⚠️ 这个「全绿」只说明**这三条**没了。§46 的教训照旧：**别把它当成「套件干净了」**。

## 52. ★ 争议锁定（规格 §3.6.5）—— 补上「写」的那一半（电脑端）

规格只有两行：「用户可给证据打标记、可锁定」+「**锁定后永不被自动清理**」
（§3.5.3② 的硬豁免）。手机端那半在 `VidLog-Mobile` 的同名提交。

⚠️ 这条**两端都只有读的那一半**：`CleanupPolicy.IsLocked` 读 `LabelKeys.Locked`
（`CleanupTests` 覆盖得很全：锁着的不清 / `'false'` 不锁 / 认不出的当锁着），
**而全仓没有任何地方写它** —— `ILabelStore.SetAsync` 唯一的生产调用点在
`UploadReceiver`（写的是手机上传时带过来的标签）。

⇒ 那条硬豁免是**结构性走不到**的：**电脑端用户没有任何办法把一条纠纷录像保住**，
保留期一到本机那份就被清了（归档层那份还在，但本机这份没了）。

### 52.1 判据收成一处（`EvidenceLock.IsLocked`）

判据本来就有、而且与手机端**同向**。问题在**界面也要判它**（那一列的文字），
而在界面里另写一份必然漏掉第三条「**认不出来的值当锁着**」
⇒ 出现「界面显示没锁、清理却把它保留了」，用户没机会理解那个状态。

所以提成一个导出函数 `EvidenceLock.IsLocked`（放在 `Labels/LabelStore.cs`，
**与手机端 `label_store.isEvidenceLocked` 同一个位置**），
`CleanupPolicy.IsLocked` 改成调它 —— **判据只有一处**。

⚠️ 这三条判据的完整理由现在写在 `EvidenceLock` 的文档注释里（含那条
「写 `'1'` 会让用户**解不开**锁」的警告）—— 原来它在 `CleanupPolicy` 的私有方法上，
而界面看不见它。

### 52.2 界面：检索结果列表多一列

`ResultsGrid` 加了一列 `DataGridTemplateColumn`：按钮文字是「锁定 / 已锁定」，
`Tag` 带着 `evidenceId`，点它走 `OnToggleLock`。

⚠️ 三处刻意的选择：
1. **当前锁没锁是从标签读的**，不是从按钮文字猜 —— 按钮文字可能是上一次检索的旧值；
2. 写完**重新检索一遍**，那一格才会跟着变（否则用户点完看不出反应）；
3. 写失败要**说出来**（I3）：用户以为锁上了而其实没锁，那条录像会在保留期到的时候被清掉。

### 52.3 ★★ 绊线的天花板：**只摘一处它挡不住**（实测出来的）

新绊线 `锁定在界面上真的有出路` 有四条断言，其中 ③ 是「判据用的是共享函数」：

```csharp
Assert.Contains("EvidenceLock.IsLocked(", window, StringComparison.Ordinal);
```

**做变红证明时它没红** —— 因为我只把 `OnToggleLock` 那一处改成了自己解析，
而**列表那一列也在用** `EvidenceLock.IsLocked(` ⇒ 断言仍然成立。
把**两处都**改成自己解析，它才红（`Sub-string not found`）。

⚠️ 而「只在其中一处用共享判据、另一处自己解析」**恰恰是这个坑最现实的形态** ——
界面上那一格写着「锁定」、点下去却是解锁。所以我把这个天花板
**写进了绊线的注释里**（而不是留着一个以为更严、其实一样的断言）。

真要根治还是那句：把 App 层做成可测的（§28.4 那两条路）。
在那之前，这条绊线的价值是「**别把这一跳整体摘掉**」—— 而那也正是它
第一次做变红证明时挡住的东西。

## 53. 机位名 12 格：电脑端原来没有那把尺子

规格 §3.4.3 ② 原话：「上限属于『机位名』**这个字段**，不只属于那个输入框……
所以从**任何路径**写进来的名字都得是同一把尺子 —— 手改过的配置文件、
旧版本存下的长名字也一样。」§3.4.5 ③ 又说：「**两端必须用同一套换算**。」

手机端早就有了（`device_identity.dart` 的 `maxDeviceNameWidth` / `deviceNameWidth` /
`clampDeviceName`，2026-09-23 那批），**而电脑端一个都没有**：
`DeviceRegistry` 直接把 `pending.DeviceName` 落盘，不截也不校验。
⇒ 手改过的登记簿、或从任何非扫码路径进来的超长名字，会在设备表里原样显示（撑破布局）；
而且「同一把尺子」只有一端有。

### 53.1 新增 `Upload/DeviceNameRules.cs`（与手机端**逐字同构**）

常量、宽度函数、截断函数三样都照手机端抄 —— 包括那张 **East Asian Width 区间表**。
⚠️ 那张表差一个区间，两端对同一个名字的格子数就不同，所以注释里写明
「必须与手机端逐字一致」。

⚠️ 两条实现上的讲究（都是手机端踩过的）：
- **不能用 `string.Length`**：它数的是 UTF-16 code unit ——「未命名机位」是 **5**
  不是 10（6 个汉字会被判成 6、全部放行，**上限放宽一倍**）；emoji 反过来算 2。
- **截断按 rune（Unicode 标量）走**：按 `char` 砍在代理对中间会留下半个字符 ——
  界面上是个豆腐块，而且是个**非法 UTF-8 序列**，传给电脑端会变乱码。

### 53.2 ★ 三处量尺，各挡一条路（都调**同一个函数**）

| 在哪 | 挡的是 |
|---|---|
| `RequestAsync`（入口） | 待批准弹窗上显示超长名字、而批准后落盘的是截过的 —— **用户看到的两处不一样** |
| `AppendAsync`（落盘） | 将来新加的任何入口；以及「盘上原始数据」这一层 |
| `LoadAllAsync`（读盘） | **这次改动之前就写进去的**：手改过的登记簿、旧版本存下的长名字 |

⚠️ 三处**调同一个函数**（不是三份实现）—— 与 §52.1 那条「判据只有一处」同一个道理。

### 53.3 ★★ 跨仓固定向量（7 条，两端同一组）

两个仓没法共享代码，所以「两端同一把尺子」需要一个物证：
**同样输入 → 同样输出**的一组样例，两边各写一份。

⚠️ 手机端**原来就有**机位名的测试（22 条），但用的是**另一组样例**
（`三号仓打包台` / `a📦📦…`）—— 也就是说**两端之间没有对齐物**：
改一端的换算，另一端**不会红**。这一批补上的正是那一组共同的样例。

**变红证明（实测过）**：把 `Width` 换成 `text.Length` ⇒ **6 条红**：

- `六格汉字是十二格_而不是六个字符`
- 向量里的 `未命名机位` / `未命名机位abc` / `打包手机-1` / `🎬录像` 四条

⚠️ 而向量里**纯 ASCII 的那两条**（`abcdefghijkl` / `abcdefghijklm`）**照常绿** ——
**那正是这个坑隐蔽的原因**：拿英文名试永远看不出问题。

⚠️ 另外两条（入网时截断 / 手改登记簿读出来也截）**没红**：它们验的是 `Clamp`，
而探针只改了 `Width`。那是**正确的**——变红配方要能指出「红的正是被改坏的那一处」。

### 53.4 ★ 一个小插曲：我自己的算术错被测试抓到了

向量里 `打包手机-1` 我写的是 **11** 格，实际是 **10**（4 汉字 8 格 + `-` + `1`）。
测试第一次跑就红了。

⚠️ 值得记的是**我当时的注释**：`// 4 汉字(8) + '-' + '1' + '1'？` —— 末尾那个问号
说明我写下时就不确定，而**测试替我把那个问号消掉了**。这就是「先写判据、
再写实现」的价格：它会把「我以为」变成「是/不是」。

## 54. ★ 技术验证：一路源同时喂「录制」与「识码」会不会互相拖垮

规格 §3.1.3（预录缓冲）要求「开始录制的动作**早于**扫码完成时刻，缓冲期内的画面也要保留」。
而电脑端现在是「空闲识码 → 扫到才开录」（需求方裁定，§24 第 3 点），两件事不重叠。
⇒ 要做到 §3.1.3 就得**在识码的同时录着**，也就是「一路源、两路输出」。

⚠️ 而 §24 第 2 条明确否决过它：「**多一路输出就多一条会堵的管道**，而堵住管道会一路顶到
ffmpeg —— 它连 `q` 都处理不了，只能强杀，MKV 尾部就丢了」。
**但那条否决的理由是「识码与录制本来就不重叠，双输出解决的是一个不存在的问题」** ——
要做 §3.1.3，它就从一个「不存在的问题」变成一个真问题，所以得**重新量一次**。

脚本：`scripts/verify-dual-output.ps1`（本机 `-Source lavfi`，有摄像头的机器 `-Source dshow`）。

### 54.1 方法：两个场景，**第二个是对照**

| 场景 | 做了什么 | 为什么要有它 |
|---|---|---|
| A 及时读 | 读管道、按 1 fps 丢（模拟识码端） | 验「及时读是不是就不堵」 |
| **B 不读** | **故意不读** | 证明这个验证方法**真的测得出堵** —— 与「先证明会红」同一个道理 ⚠️ 若它也不堵，A 那个绿不算数 |

### 54.2 结果（本机实测）

| 场景 | 退出 | 耗时 | 产物 | 可解码 |
|---|---|---|---|---|
| **A 及时读** | 退出码 0 | **10.2 秒**（源 10 秒） | 389 755 字节 | ✅ true |
| **B 不读** | **超时被堵住** | 105.1 秒 | 262 144 字节（半截） | ⛔ false |

⚠️ **B 复现的正是 §24 描述的那个现象**：堵住 → 只能强杀 → MKV 尾部丢了 → 解不开。
所以那条警告**是真的**，不是推测。

### 54.3 结论

**可行，但有一条硬前提**：识码那一路必须**及时读、且跟得上产出**。

⇒ 实现上的条件是：
1. 识码那一路**降帧到 1 fps**（`-vf fps=1,scale=640:480`）—— 降帧之后管道的产出速率
   就是 1 帧/秒（640×480 灰度 = 307 KB/s），**读取端余量极大**；
2. 读取端**永不阻塞**（独立线程；万一跟不上，宁可丢识码帧，**绝不让录制等它**）。
   ⚠️ ffmpeg 的管道是**有序的**、不能跳帧 —— 所以「丢帧」只能靠**读得比产出快**来实现，
   而 1 fps 下这很容易做到。

⚠️ **但「技术可行」不等于「应该做」**：§3.1.3 与那条需求方裁定（「空闲时识码、扫到才开录」）
**仍然是打架的**，而那是需求层面的取舍（宁可丢 1.8 秒画面 vs 担一路管道被堵死的风险）。
这次验证把「能不能做」回答了，**「要不要做」归需求方**。

### 54.4 途中的两个发现（都值得记）

1. ★★ **`-t` 是「每一路输出各自的选项」，不是全局的。**
   第一版只给第一路输出加了 `-t 10`，第二路（`pipe:1`）没有 ⇒ lavfi **无限生成**、
   ffmpeg 永不退出（挂到 600 秒超时）。
   ⚠️ 而且**连 OS 级的 `> NUL` 重定向也一样挂** —— 它把「卡在读取端」这个假设
   直接排除了，才定位到是命令本身的问题。
   ⇒ 这本身就是双输出的一条实现约束：**每一路都要各自限长**。

2. ⚠️ **我自己也踩了一次「管道要读干」**：脚本第一版对 stderr 设了重定向却**从不读它**，
   ffmpeg 卡在写 stderr 上 —— 与 §24 记的是同一件事，只不过那次是 stdout。
   （修法：起一个 `ReadToEndAsync` 任务，且**与场景无关地**读 ——
   否则 B 场景就分不清到底堵在哪一路。）

### 54.5 仍未验的（诚实边界）

⚠️ **`-Source lavfi` 验的是管道背压机制，验不到 dshow 那一层**：
相机缓冲、yuyv422 → yuv420p 的转换代价、以及 §25 实测的那 1.5 秒打开延迟。

## 55. 重复单号检测（规格 §3.2.5）—— 一条被划错了区域的欠账

### 55.1 ★ 它不是「依赖服务端」，它是纯本地能力

规格 §3.2.5 标题是「**电脑端专属**识别行为」，下面三条：

| 条 | 要什么 |
|---|---|
| **重复单号检测** | 「识别到的单号若在近 N 天内已有未删除记录，必须提示。N 可配置。」 |
| 订单联动 | 从浏览器侧同步订单信息 —— 要服务端 |
| 退款拦截 | 后台周期性查询「打印后退款」列表 —— 要服务端 |

⚠️ 而实现方此前把**三条一起**记成了「依赖服务端，服务端未开工」（`实现决策.md:215`、`README.md`）。
**那个划分对第一条是偏宽的**：「近 N 天内已有未删除记录」问的是**本地索引**
（`RecordingIndex` 里就有那些数据），一行网络都不需要。

⇒ 后果是：同一单号近期录过时用户收不到任何提示，**重复录件 / 单号扫错都发现不了**
—— 而那是这条唯一要做的事。

### 55.2 实现：注入一个探测委托（协调器仍然不碰索引）

`RecordingCoordinator` 加可选参数
`duplicateProbe: Func<WaybillNumber, CancellationToken, Task<IReadOnlyList<RecordingEntry>>>`，
**默认 null = 不检测**。生产那边接的是 `RecordingSearch.SearchAsync`
（它的「按单号精确查」+ 单号归一化已经在了，再写一份必然走岔）。

⚠️ 与 `RecordingSession` 的 `durationPrompted` 同一个手法：**协调器不该知道检索那一层**。
⚠️ 关掉时（天数 ≤ 0）**根本不给这个委托** ⇒ 连一次索引都不读。

**设置**：`AppSettings.DuplicateCheckDays`，默认 **7 天**（规格没给数，本仓标定），
**0 = 关闭**（规格说「N 可配置」，那就得允许关 —— 一个关不掉的提醒在连续扫的工位上
就是噪声，而噪声会被无视）。界面上那行写明了「只提醒、不挡开录」和「填 0 关掉」。

**提示出口**：托盘气泡 **+ 语音**（`App.OnNotice`，与闲置提醒同一族）——
操作员这时手上正拿着包裹，**很可能没看屏幕**，光弹气泡等于没说。

### 55.3 ★★ 「绝不阻塞开录」是怎么验的

规格那条的硬约束是「这三项**全部异步执行，绝不阻塞开录**」。
所以最有力的一条测试是：**让探测永远不返回**，然后断言**开录照样完成**：

```csharp
var never = new TaskCompletionSource<IReadOnlyList<RecordingEntry>>();
... duplicateProbe: (_, _) => never.Task ...
await coordinator.SubmitAsync(A, PunchSource.KeyboardScanner);
Assert.Equal(A, coordinator.CurrentWaybill);   // ★ 开录回来了、而且真的在录
```

**变红证明（实测过）**：把 `_ = CheckDuplicateWaybillAsync(...)` 改成
`await CheckDuplicateWaybillAsync(...)` ⇒ 用 `--blame-hang-timeout 40s` 跑，
报告 **「指定的非活动时间(40 秒)已过，正在收集挂起的转储」** ——
即**测试挂住了**。⚠️ 这个红的形态本身就是问题本身（开录永远完不成），
比一条断言失败更说明问题。

### 55.4 ★ 那条「N 天以外的不提示」差点绿在巧合上

它要验的是「30 天前录的不提示」。但**检测是异步的** —— 直接断言「没有通知」的话，
它可能只是因为**检测还没跑**，而不是因为窗口筛对了。

⇒ 加了一个 `queried` 标志，**先等「探测真的被调过」再断言「没提示」**。
少了这一步，那条测试测的就不是窗口，而是「跑得够不够慢」。

### 55.5 验证状态

桌面端 **601 通过 / 2 跳过**（597 → 601：4 条检测用例）。
`dotnet build` 0 警告，`precheck.ps1` 全绿。

⚠️ **只有真机能验的**：语音真的念出来、气泡真的弹出来（`Speech` / 托盘在本机没有窗口与
语音引擎）。本机验的是判定、窗口筛选与「不阻塞开录」。

⚠️ **仍未做的**：订单联动与退款拦截——那两条**确实**要服务端（M6）。

## 56. 二次改名要电脑端同意（规格 §3.4.5 ③）

需求方 2026-09-24 原话：「……用户编写确认后，电脑端显示手机端的名字，并且以后该手机端
连接电脑端都是这个名字，**如需要再次更改，需要电脑端同意才能更改**。」

⚠️ 在此之前**没有任何改名通路**：手机端 `rename()` 只改本机，电脑端要等下次报到
才看到新名字 —— 而「需要电脑端同意」这条**根本不存在**。手机端那半在
`VidLog-Mobile` 的同名提交。

### 56.1 ★ 改名的待批准**刻意不复用**入网那一个

`PendingEnrollment` 那批是**绑在「屏幕上那张二维码」的生命周期上**的
（换一张码就把它们全清掉）。而**改名没有二维码** —— 它靠设备自己的凭据。

混在一起的话，「用户又点了一次【连接电脑/手机】」会把一条正在等的改名请求
**一起清掉**，而手机上还在轮询，**看不出为什么**（它只会一直等，等到自己的上限）。

所以 `_renamePending` 是**独立**的一个字典。⚠️ 但**界面复用同一套人工批准交互**
（规格原话「走同一套弹窗通道」）。

### 56.2 ★ 界面那一格不能挂在 `EnrollWindow` 上

`EnrollWindow` 的轮询是 `(await registry.PendingAsync())` —— 而那个方法在
「屏幕上没有可用二维码」时返回空。改名请求**没有二维码**，所以它在那里
**永远看不到**。

⇒ 改名由 `MainWindow` 自己轮询（2 秒一次）。⚠️ 那个轮询**一直跑**，
与录音状态那个**按需启停**的 `_ticker` 不同：改名请求不挑时候，窗关着也得能收到。

### 56.3 报文里没有 `deviceId`（安全边界）

`RenameRequestPayload` **只带 `deviceName`** —— 身份来自 `Authorization: Bearer`
凭据反查出来的那台设备。让客户端自称 id 的话，任何一台已入网设备都能改**别人**的名字。
这与 `UploadReceiver` 那条「身份从凭据来」是同一条规矩。

### 56.4 两条刻意的方向

| 做法 | 为什么 |
|---|---|
| 批准时**用同一个凭据**追加一条新名字（`AppendAsync(device with { DeviceName = … })`） | 改名**不是**重新入网。换了凭据那台手机下一次上传会撞 401，而它以为只是改了个名字 —— 表现是「改完名字就传不上来了」 |
| **拒绝也留着**那条请求 | 与入网那条同一个理由：手机在轮询，清掉的话它下一轮拿到「没有这条请求」，而用户明明刚被拒 |

### 56.5 ★ 测试第一次跑抓到的是**夹具错**，不是实现错

我给测试设备起名 `打包手机-phone-1`（**15 格**），而断言「改名后名字是 X」时拿到的是
`打包手机-pho`。原因：入网那条路**已经会**被 12 格的尺子截断（§53 加的那把尺子）。

⇒ **那是实现正确**，我的夹具本身超长。改成 `机位-phone-1`（正好 12 格）之后全绿。

⚠️ 值得记的是这个巧合：如果 `打包手机-phone-1` 恰好不超过 12 格，
这条测试会**一直绿着**，而它断言的「名字没变」其实是在断言「名字被截过」——
夹具的名字长度意外地成了测试的一部分。

### 56.6 判据抽成一处产出（手机端）

手机端「要不要请电脑端同意」的判据是**有没有凭据**：
没入网 ⇒ 这次命名是入网那一步的一部分（电脑端同意连接时已经同意过了）；
已入网 ⇒ 上面那句原话适用。

⚠️ 抽成 `DeviceIdentity.renameNeedsApproval` 是为了**能测** ——
界面那一层在 widget 测试里碰不到（`_sessions` 恒空），而这个判据决定了
「要不要去麻烦另一头的人」。

### 56.7 验证状态

桌面端 **607 通过 / 2 跳过**（601 → 607：改名 5 条 + 界面绊线 1 条）；
手机端 **600 通过**（599 → 600：判据 1 条）；两端 analyze/build 0 警告。

⚠️ **只有真机能验的**：那个弹窗真的弹出来、点了同意之后手机上的名字真的变

⚠️ 而**等待必须是看得见的**（I3 的精神）：手机端每轮把「已经等了多久」写到状态行上，
并有 5 分钟上限（与入网那张码同量级）—— 否则用户分不清「没人理」和「程序卡了」。

### 56.8 ⚠️ 我自己的流程错：`git add -A` 把一个 0 字节垃圾提交了

做这条时我用 PowerShell 批量改一个测试文件（`cd` 没生效 ⇒ 相对路径落在**仓根**），
那句 `WriteAllText` 因为拿到 null 而抛异常 —— **但它已经先把文件创建出来了**。
于是仓根留下一个 **0 字节的 `RenameApprovalTests.cs`**，
而我没看 `git status` 就 `git add -A`，把它和真正的改动一起提交了。

⇒ 两条教训：
1. **`git add -A` 之前先看 `git status`**。这个仓一直有这个习惯，
   而这次省了那一步就出事 —— 而它的表现极其安静（0 字节的文件不影响编译、
   不影响测试，`dotnet build` 照样 0 警告）。
2. **PowerShell 的 `cd` 不跨命令持久**（每次工具调用是一个新 shell）。
   我前面几百次命令都写成 `cd X; ...` 一条，这次漏了 ⇒ 相对路径落到仓根。
   ⚠️ 而失败信息（`Could not find file 'D:\VidLog-Desktop\RenameApprovalTests.cs'`）
   **已经把这件事说出来了** —— 我当时只看到「找不到文件」，
   没读出「所以它现在在仓根找」。**报错信息里的路径是证据。**

已用一个删除提交清掉它。
